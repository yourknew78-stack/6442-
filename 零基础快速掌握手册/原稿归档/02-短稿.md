# 02｜测试：让每个用例都有理由

> 一句话：**测试用例 = 输入 + 预期结果 + 一次实际调用。** 先看题目要覆盖代码，还是要核对文字规格。

## 先认题型

| 题面关键词 | 该做什么 | 重点 |
|---|---|---|
| `branch complete`、`minimum` | 白盒：覆盖每个条件的真、假出口，用例数尽量少 | 画覆盖表 |
| `statement coverage`、`code complete` | 白盒：让每条要求的语句执行至少一次 | 特别检查 `throw`、`return` |
| 给多个实现，要求正确的通过、错误的失败 | 黑盒：按 README 的规格写断言 | 期望值自己算 |
| 要求测试异常 | 确认指定异常确实被抛出 | 异常类型要准确 |

**先读原题的计数和扣分规则。** 参数化测试通常一行数据算一个用例；有些题把每次断言算一个用例。按骨架和 README 判断。

## 1. 一个断言到底在检查什么

```java
assertEquals(12, Pricing.calculatePrice(3, 4, "id1"));
```

左边 `12` 是你**预先算出的期望值**，右边是程序的实际结果。若返回类型是对象，注意 JUnit 的重载：必要时用 `Integer.valueOf(12)`，或对实际的 `Integer` 调 `.intValue()`。

| 断言 | 用来检查 |
|---|---|
| `assertEquals(expected, actual)` | 两个值相等 |
| `assertTrue(condition)` / `assertFalse(condition)` | 布尔结果 |
| `assertSame(a, b)` | 是不是同一个对象 |
| `fail("reason")` | 执行到这里就应判失败 |

断言执行成功只说明**这一组输入**符合你的预期；不会自动证明其他输入正确。

## 2. 分支覆盖：先看真、假，再挑输入

例子：

```java
if (a < 0 || b < 0) return 1;
return 0;
```

这门课的相关题目把 `&&`、`||` 的子条件也作为分支看待。所以要分别考虑 `a < 0` 和 `b < 0` 的真、假。又因为 `||` **短路**：当 `a < 0` 为真时，右边的 `b < 0` 根本不执行。

| 输入 `(a,b)` | `a<0` | `b<0` | 返回 |
|---|---|---|---:|
| `(-1, 0)` | 真 | 未执行 | 1 |
| `(0, -1)` | 假 | 真 | 1 |
| `(0, 0)` | 假 | 假 | 0 |

这三行覆盖了两个子条件各自的真、假出口。右边条件的两种结果都必须在左边为假时制造。

### 最少用例的做法

1. 把目标方法的每个 `if`、`else if`、循环条件列出来；按原题口径拆开 `&&`、`||`。
2. 给每个条件画“真 / 假”两格。
3. 从最难到达的格子倒推输入。一次调用能顺便覆盖其他格子，就合并。
4. 每组输入手算结果，写进断言。
5. 最后删掉没有带来新覆盖、且题目要求最少用例的行。

**不要把“条件有多少出口”直接当作最少用例数。** 一次调用通常会经过多个条件。

## 3. 走一个真实例子：2025 S2 Pricing

原题要求用最少的参数化测试覆盖 `calculatePrice` 的分支，而且多一行或少一行会扣分。见 [原题 README](../exam-practice-questions/past-exams/2025-2/src/Q2/Q2README.md)。

以下是原稿中按原题骨架验证过的 7 行数据。先看每行**负责哪条独特路径**，不要先背数字：

| 输入：单价、数量、会员 | 主要目的 | 预期 |
|---|---|---:|
| `3, null, null` | 数量为空，会员也为空 | 12 |
| `3, null, ""` | 会员非 null 但修剪后为空 | 12 |
| `3, null, "id1"` | 会员非空 | 12 |
| `3, 4, "id1"` | 数量既不小于等于 3，也不大于等于 5 | 12 |
| `3, 5, "id1"` | 会员在名单内，单价达到门槛 | 10 |
| `3, 5, "other"` | 会员不在名单内，整数除法 `5/6=0` | 15 |
| `2, 6, "id1"` | 单价没到门槛，整数除法 `6/6=1` | 10 |

关键不是“7 行”这个数字，而是**每行打中哪些之前没打中的真 / 假出口**。原稿有完整条件矩阵和 `data()` 代码，见[详细版的 2025 S2 小节](原稿归档/02-testing.md#41-2025-s2-q2-pricing-最少分支覆盖)。

注意：数量非空时，会员 `null` 可能让原题中的 `List.of(...).contains(memberId)` 抛异常。这种行不能用来充覆盖。

## 4. 黑盒测试：从规格推期望

白盒看代码路径；黑盒看**题目承诺的行为**。多个实现供测试时，先把 README 拆成规则表：

| 规格条款 | 输入 | 期望 |
|---|---|---|
| 正常情况 | 一个普通值 | 手算结果 |
| 边界 | 恰好在阈值上、阈值前后 | 分别手算 |
| 非法输入 | 题目列出的无效值 | 指定异常或返回值 |

每一行的期望值应从规格算出。不要运行某个实现后把它的输出抄成期望值，因为那个实现可能正是错误版本。黑盒题如果没有最少用例惩罚，可为不同规则分别写测试，便于定位错误。

## 5. JUnit 4 常见写法

### 参数化测试：只改题目让你改的地方

如果骨架有带参数构造器，`data()` 的每一行按**构造器参数顺序**填：

```java
@Parameterized.Parameters
public static Collection<Object[]> data() {
    return Arrays.asList(new Object[][] {
        {3, 4, "id1", 12},
        {3, 5, "id1", 10}
    });
}
```

如果骨架用 `@Parameter(0)`、`@Parameter(1)` 字段注入，则列号对应字段；不要再加带参数构造器。返回类型、类名和方法签名照原题保持。

### 异常测试：最短的一种

```java
@Test(expected = IllegalArgumentException.class)
public void rejectsNegativeQuantity() {
    Calc.price(3, -1);
}
```

它只适合整个测试方法就是为了检查这次异常。若还需检查异常消息或多次调用，可用 `assertThrows`（先确认原题 JUnit 版本支持）。异常类型用题目指定的具体类。

## 6. 考场检查顺序

1. 读清是分支覆盖、语句覆盖，还是黑盒规格测试。
2. 核对“一个用例怎么算”和是否要求最少数量。
3. 白盒：画真 / 假表，处理短路；黑盒：列规格、边界、非法输入。
4. 为每行写清输入、预期值、覆盖目的。
5. 运行测试；确认没有意外异常或写反的断言。
6. 最少用例题，删除没有新增覆盖的行，再核查全部格子。
