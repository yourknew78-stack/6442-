**占位符约定：**下文所有模板里，带 `←` 的行都要改；其余是固定写法。占位符含义如下，改题时按此替换一次即可，不必逐行纠结。

| 占位符 | 换成什么 | 例子 |
|---|---|---|
| `Target` | 题目里的**被测类名** | `Person`、`StringUtil`、`MyInteger` |
| `TargetTest` | 你的测试类名，必须与文件名一致 | `PersonTest` |
| `target` | `new` 出来的被测对象 | `Person p = new Person(...)` |
| `actual` | 被测方法返回的**实际值** | 不用改，变量名而已 |
| `expected` | 你**手算**的期望值 | 期望写在 `assertEquals` 的第一个参数 |
| `a`、`b`、`i` | 题目方法的参数 | 按签名顺序填 |
| `hashingBox`、`tree`、`bc` | 原题骨架**已有**的对象，保持原名，不要改 | — |

**复制前四件事：**保留原 `package`；只在允许的 TODO 区改；保留框架传入的被测对象；先读“最少”究竟数数据行、调用、断言，还是树的总节点。模板中 `Target`、`target`、`input` 等名字是待替换占位符，不是题库自带类。

## T1｜普通测试骨架（JUnit 4 与 JUnit 5 二选一）

**什么时候用**：题目要你自己建测试类，或只给了一个空的 `@Test`。

**怎么用**：整块复制 → 把标 `←` 的地方换成题目的类名／方法／参数／期望 → 运行。跑红只说明期望值算错，先别怀疑代码。

### T1-A：JUnit 4

```java
import org.junit.Test;
import static org.junit.Assert.*;

// ← 类名 = 被测类名 + Test，必须和文件名一致
public class TargetTest {

    @Test
    public void testNormal() {
        // ← 3、4 换成题目给的输入
        int actual = Target.calculate(3, 4);

        // ← 12 换成你手算的期望
        // 参数顺序固定是：期望在前，实际在后
        assertEquals(12, actual);
    }
}
```

**如果题目方法是实例方法**（不是 static），先 `new` 出对象：

```java
// ← 构造参数按原题填；没有参数就保留空括号
Target target = new Target();

// ← 换成题目里的方法名和输入
int actual = target.calculate(3, 4);

assertEquals(12, actual);
```

### T1-B：JUnit 5（2019 S1 原骨架）

```java
import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.*;

class TargetTest {

    @Test
    void testNormal() {
        assertEquals(12, Target.calculate(3, 4));
    }
}
```

**两个版本不要混用**，差别一张表看完：

| 项目 | JUnit 4 | JUnit 5 |
|---|---|---|
| 注解的包 | `org.junit.Test` | `org.junit.jupiter.api.Test` |
| 测试方法的写法 | 必须 `public void` | 可以 `void` |
| 期望异常 | `@Test(expected = X.class)` | `assertThrows(X.class, …)` |
| 超时 | `@Test(timeout = 1000)` | `assertTimeout` 系列 |
| 失败提示放哪 | 第一个参数 | 最后一个参数 |

**按题目已经给的 import 选版本**，不要自己换。2019 S1 是 JUnit 5；2020 S2、2021 S2 明确要 JUnit 4。

## T2｜断言积木：按需要挑一行抄进测试方法

断言是"比赛裁判"：它写清楚期望，运行后自动判定通过还是失败。

| 断言 | 什么时候用 | 写法示例 |
|---|---|---|
| `assertEquals(期望, 实际)` | 整数、字符串、`Integer`、列表 | `assertEquals(12, actual);` |
| `assertEquals(期望, 实际, 误差)` | **浮点数必须带误差** | `assertEquals(12.5, actual, 0.000001);` |
| `assertArrayEquals(期望, 实际)` | 数组逐元素比较 | `assertArrayEquals(new int[]{1,2,3}, arr);` |
| `assertTrue(条件)` / `assertFalse(条件)` | 布尔结果 | `assertTrue(ok);` |
| `assertNull(对象)` / `assertNotNull(对象)` | 是否为 null | `assertNull(id);` |
| `assertSame(a, b)` / `assertNotSame(a, b)` | 是否**同一个对象**（比身份，不比内容） | `assertSame(p, returned);` |
| `fail("说明")` | 走到这里就该失败，比如"本该抛异常" | `fail("应抛异常");` |

三条最常踩的坑：

- **数组别用 `assertEquals`**，它比的是引用，一定失败；用 `assertArrayEquals`。
- **不要把被测方法再抄一遍当期望**：`assertEquals(target.f(x), target.f(x))` 没有独立期望，还多调用一次；应先手算出数，写死成 `12`。
- **`Integer` 与 `int` 的歧义**：`assertEquals(12, actualInteger)` 可能选错重载，写成 `assertEquals(Integer.valueOf(12), actualInteger)` 或 `actualInteger.intValue()` 更稳。

**失败提示的位置，两个版本相反：**

```java
// JUnit 4：提示写在最前面
assertEquals("数量恰好等于门槛", 12, actualInt);

// JUnit 5：提示写在最后面
assertEquals(12, actualInt, "数量恰好等于门槛");
```

## T3｜参数化骨架：一个测试方法跑多行输入

**这是近两年的新趋势，要按"会考"准备。** `@RunWith(Parameterized.class)` 在 2019–2023 的真题里一次都没出现；从 2024 S1 起连续三届都有，没有回落迹象：

| 年份 / 题 | 参数化的对象 | 题目给的骨架 |
|---|---|---|
| 2024 S1 Q2 `AVLTreeTest` | 数据行 `{树编号, 前序期望}` | 整个类都给，只在 `data()`、`createTree()` 留 TODO |
| 2024 S2 Q2 `Q2Test` | **实现对象** `Iterable<HashingBox>` | `getImplementations()` 注明 Do NOT Modify；`@Parameter` 字段已声明，留测试方法 TODO |
| 2025 S2 Q2 `CalculatePriceTest` | 数据行 `{Pricing, 期望}` | 整个类都给，只在 `data()` 留 TODO |

外形上有两种，别混：

- **数据行参数化**：`Object[][]` + 构造器 + 字段，一行数据跑一次 → T3-A、T4、T12；
- **实现对象参数化**：`Iterable<T>` + `@Parameter` 字段，一个实现跑一次 → T3-B、T11-B。

近三届都是"给骨架、只填空"，但下面 **T3-A 仍保留完整写法**：新题万一只给你一个空文件，你得能自己把 `@RunWith`、构造器、字段、`data()` 全部搭起来。这部分是兜底，不是让你现在背。

### T3-A：构造器接数据（JUnit 4）

**什么时候用**：题目出现 `@Parameterized`，或要求"每组输入一行"。
**怎么用**：整块复制；只改 `data()` 里的数据行。

```java
import org.junit.Test;
import org.junit.runner.RunWith;
import org.junit.runners.Parameterized;
import java.util.Arrays;
import java.util.Collection;
import static org.junit.Assert.*;

@RunWith(Parameterized.class)
public class TargetTest {

    // 一列一个字段，顺序必须和数据行的列顺序一致
    private final int a;

    // 需要传 null 的这一列要用 Integer，不能写 int
    private final Integer b;

    private final int expected;

    public TargetTest(int a, Integer b, int expected) {
        this.a = a;
        this.b = b;
        this.expected = expected;
    }

    // ← 只改这里：一行 = 一组输入 + 期望
    // 这行标记「下面是数据源」，必须保留
    @Parameterized.Parameters
    public static Collection<Object[]> data() {

        // 一行 = 一组数据；列的顺序必须和上面字段一致：a, b, expected
        return Arrays.asList(new Object[][] {

            // 第 1 个元素 a=3，第 2 个 b=4，第 3 个 expected=12
            {3, 4, 12},

            // 第 1 个元素 a=0，第 2 个 b=4，第 3 个 expected=0
            {0, 4, 0}
        });
    }

    @Test
    public void testResult() {
        // ← 换成题目里的方法，参数按 a、b 顺序填
        assertEquals(expected, Target.calculate(a, b));
    }
}
```

**四条硬性规则**（写错就编译不过）：

| 位置 | 必须写成 |
|---|---|
| `data()` | `public static`，返回 `Collection<Object[]>` |
| 测试方法 | **不能**是 `static` |
| 构造器名 | 与类名完全相同 |
| 每行数据 | 列数、类型与字段一一对应 |

### T3-B：字段注入（不写构造器的另一种写法）

**什么时候用**：题目骨架里已经有 `@Parameterized.Parameter` 字段；或者你不想写构造器。

**和 T3-A 的唯一区别是"数据怎么进到测试类"：**

| | T3-A 构造器 | T3-B 字段注入 |
|---|---|---|
| JUnit 怎么把这一行交进来 | `new TargetTest(3, 4, 12)` | 先 `new TargetTest()`，再**直接给字段赋值** |
| 需要写构造器吗 | 必须写 | 不需要 |
| 字段怎么声明 | `private final` 都行 | 必须 `public`，**不能** `final` |
| 用哪个注解 | `@Parameters`（复数，贴在方法上） | `@Parameter`（单数，贴在字段上） |

```java
import org.junit.Test;
import org.junit.runner.RunWith;
import org.junit.runners.Parameterized;
import java.util.Arrays;
import java.util.Collection;
import static org.junit.Assert.*;

// 和 T3-A 一样，必须有这行 runner，否则 @Parameter 不生效
@RunWith(Parameterized.class)
public class TargetTest {

    // ── 字段注入区：不写构造器，JUnit 直接给下面三个字段赋值 ──
    // 括号里的数字 = 取该行数据的第几个元素，从 0 开始

    // 第 0 个元素 → a
    @Parameterized.Parameter(0)
    public int a;

    // 第 1 个元素 → b
    @Parameterized.Parameter(1)
    public Integer b;

    // 第 2 个元素 → expected
    @Parameterized.Parameter(2)
    public int expected;

    // ── 数据源：和 T3-A 一字不差，仍然是 static 方法 ──
    @Parameterized.Parameters
    public static Collection<Object[]> data() {
        return Arrays.asList(new Object[][] {
            {3, 4, 12},
            {0, 4, 0}
        });
    }

    // ── 测试方法：直接用字段，不用从参数拿 ──
    @Test
    public void testResult() {
        // ← 换成题目里的方法
        assertEquals(expected, Target.calculate(a, b));
    }
}
```

**整块就是一个能跑的文件，和 T3-A 的差别只有两处**：① 没有构造器，改成三个 `public` 字段；② `testResult()` 里的 `a`、`b`、`expected` 来自字段，不是方法参数。

**跑一行时，JUnit 实际按这个顺序做**（以 `{3, 4, 12}` 为例）：

| 步骤 | 动作 | 此时 a / b / expected |
|---|---|---|
| 1 | `new TargetTest()`（无参构造器） | `0 / null / 0` |
| 2 | 按 `@Parameter(0)` 把 `row[0]` 写进 `a` | `3 / null / 0` |
| 3 | 按 `@Parameter(1)` 把 `row[1]` 写进 `b` | `3 / 4 / 0` |
| 4 | 按 `@Parameter(2)` 把 `row[2]` 写进 `expected` | `3 / 4 / 12` |
| 5 | 跑 `@Test` 方法 | 读到 `3 / 4 / 12` |

**三条限制，违反任意一条都跑不通：**

| 限制 | 为什么 |
|---|---|
| 字段必须 `public` | JUnit 是**直接赋值**，`private` 写不进去 |
| 字段不能 `final` | 每行数据都会重新赋一次值，`final` 编译就过不了 |
| 下标不能省 | 都不写时默认都是 0，三列全取第 0 个元素，`a`、`b`、`expected` 全变成 `3`，断言必错——这就是"全撞在一起" |

**真题里的另一类用法**：2024 S2 Q2 的 `Q2Test` 写的不是数据列，而是**被测实现**：

```java
@Parameter
public HashingBox hashingBox;   // 骨架给的，不要改名
```

配合题目给的 `getImplementations()` 返回 13 个实现，JUnit 就把「每个实现」当一组参数：每个实现建一次测试对象、塞进 `hashingBox`、跑一遍整个类。此时**不要**把字段改成 `int a` 这种数据列写法。

**T3-A 与 T3-B 二选一**：同一个类里用构造器就别再声明 `@Parameter` 字段，反之亦然，混用会让 JUnit 不知道按哪种方式传参。

## T4｜2025 S2 Pricing：只改 `data()`

**任务：填入数字。**

源码 `calculatePrice()` 里有几个分支，题目要你用**最少的数据行**让每个分支都跑到。`data()` 就是一张用例表——每行 = 一组输入 + 这组输入应返回多少；JUnit 拿每行跑一次测试。只管填数字，不写逻辑。

### 第 1 步：看懂源码，期望值都是从这儿来的

```java
public static Integer calculatePrice(int unitPrice,
                                     Integer quantity,
                                     String memberId) {
    double discount = 0.0;

    // 分支 1：数量为 null
    if (quantity == null) {
        discount -= 0.2;
        quantity = 1;

        // 分支 1 内层：会员号 null 或只有空白
        if (memberId == null || memberId.trim().isEmpty()) {
            discount -= 0.1;
        }
    }

    // 分支 2：数量 <= 3
    if (quantity <= 3) {
        return unitPrice * 4;
    }
    // 分支 3：数量 >= 5
    else if (quantity >= 5) {

        // 分支 3 内层：在名单里且单价 >= 3
        if (List.of("id1", "id2", "id3").contains(memberId)
                && unitPrice >= 3) {
            return 10;
        }
        // 分支 3 另一条：数量够一打，减掉 1/6
        else if (quantity / 6 >= 1) {
            quantity -= quantity / 6;
        }
    }

    return (int) (unitPrice * quantity * (1 - Math.min(discount, 0)));
}
```

### 第 2 步：每行的期望值是这样算出来的

| # | 输入 `(unitPrice, quantity, memberId)` | 走哪条分支 | 计算过程 | 期望 |
|---|---|---|---|---|
| 1 | `(3, null, null)` | 数量 null；会员号也 null | 数量改成 1 → `<=3` → `3×4` | 12 |
| 2 | `(3, null, " ")` | 数量 null；会员号是空白串 | 同上 | 12 |
| 3 | `(3, null, "id1")` | 数量 null；会员号非空 | 同上 | 12 |
| 4 | `(3, 4, "other")` | 两个主分支都不进 | `3×4×1` | 12 |
| 5 | `(3, 5, "id1")` | `>=5`、在名单、单价 `>=3` | 源码直接 `return 10` | 10 |
| 6 | `(3, 5, "other")` | `>=5`、不在名单，`5/6=0` | `3×5` | 15 |
| 7 | `(2, 6, "id1")` | `>=5`、在名单但单价 `<3`，`6/6=1` | 数量变 `6−1=5` → `2×5` | 10 |

两个容易看晕的点：

- **行 1–3 都是 12**，不是因为折扣算出来一样，而是 `quantity` 为 null 时源码先把它改成 `1`，立刻走 `quantity <= 3` 就 `return unitPrice * 4` 了。这三行是为了覆盖"会员号 null／空白串／非空"三个内层方向。
- **行 4 的 12 是巧合**：`3×4=12` 与行 1 同数字，但走的是完全不同的一条路。

### 第 3 步：这 7 行分别覆盖哪个分支

| 源码分支 | 由哪行覆盖 |
|---|---|
| `quantity == null` 且会员号为 null | 行 1 |
| `quantity == null` 且会员号为空白串 | 行 2 |
| `quantity == null` 且会员号非空 | 行 3 |
| 两个主分支都不进（数量 4） | 行 4 |
| `>=5`、在名单、单价 `>=3` | 行 5 |
| `>=5`、不在名单，`5/6=0` 不成立 | 行 6 |
| `>=5`、在名单但单价 `<3`，`6/6=1` 成立 | 行 7 |

### 第 4 步：粘贴位置

题目给的骨架长这样（`CalculatePriceTest.java`，**已经存在，照原样保留**）：

```java
// 原文件里已有：注解、方法签名、字段、构造器、@Test 都不要动
@Parameterized.Parameters(name = "{index}: isValid({0}) = {1}")
public static Collection<Object[]> data() {
    // TODO - Start your code here

    return Arrays.asList(new Object[][]{
            //  Add your test cases here, e.g.
            // {new Pricing(3, 1, "id1"), 10},

    });

    // TODO - End your code here
}
```

只把 `// TODO` 之间那段 `return` 换成下面这份：

```java
@Parameterized.Parameters(name = "{index}: isValid({0}) = {1}")
public static Collection<Object[]> data() {

    // 每行的形状固定是：{ 输入对象, 期望价格 }
    // new Pricing(unitPrice, quantity, memberId)，三个参数顺序不能错
    return Arrays.asList(new Object[][] {

        // 为什么传 null：要进「数量为 null」那个 if
        // 为什么会员号也传 null：要让内层「null 或空白」为真
        // 为什么是 12：源码把数量改成 1 → 1 <= 3 → 3 * 4
        {new Pricing(3, null, null), 12},

        // 数量仍为 null；会员号给空白串，让 trim().isEmpty() 为真
        // 走的路和上一行一样，所以还是 12
        {new Pricing(3, null, " "), 12},

        // 数量 null；会员号非空，内层判断为假（覆盖「假」这一边）
        // 仍是 1 <= 3 → 3 * 4 = 12
        {new Pricing(3, null, "id1"), 12},

        // 为什么数量给 4：既不 <= 3，也不 >= 5，两个主分支都跳过
        // 直接落到最后一行 return：3 * 4 * (1 - 0) = 12
        {new Pricing(3, 4, "other"), 12},

        // 为什么给 5：进入 >= 5 分支
        // 为什么会员号给 id1、单价给 3：内层要求「在名单且单价 >= 3」
        // 源码这一路直接 return 10，不是乘出来的
        {new Pricing(3, 5, "id1"), 10},

        // 数量 5 但不在名单：内层 if 为假
        // 5 / 6 = 0，不满足 >= 1，else-if 也为假
        // 落到最后 return：3 * 5 = 15
        {new Pricing(3, 5, "other"), 15},

        // 为什么单价给 2：在名单但单价 < 3，让内层 if 为假
        // 6 / 6 = 1，数量减成 5，落到最后 return：2 * 5 = 10
        {new Pricing(2, 6, "id1"), 10}
    });
}
```

`Pricing` 构造器参数顺序是 **(unitPrice, quantity, memberId)**。骨架注释里那行示例 `{new Pricing(3, 1, "id1"), 10}` 的期望值是错的（按源码应得 12），**别照抄那个 10**。

### 为什么是 7 行，能不能 6 行

把短路求值展开来数：空数量 3 种走法 + 数量 4 一种 + 后段 AND 3 种 = 7。若题目只按完整 `if` 的真假统计、不拆短路，可删第 2 行变 6 行。原题未公开更细的评分口径，**不要无条件把 7 当成官方答案**。

**两条通用规则**：① 格式永远是 `{new 参数类(输入…), 期望}`；② `quantity >= 5` 时别传 `memberId = null`，否则名单查询可能抛异常，而原题禁止异常用例。

## T5｜分支覆盖：if、else-if、短路条件

### T5-A：照着源码结构挑输入

| 源码结构 | 输入要凑出哪些情况 | 常见遗漏 |
|---|---|---|
| `if (A)` | A 真、A 假 | 没写 `else` 也有"跳过"的假分支 |
| `if (A) … else if (B) … else` | A真；A假B真；A假B假 | A 真时 B 根本不执行 |
| `if (A) { if (B) … }` | A真B真；A真B假；A假 | 通常至少 3 次 |
| 两个独立 `if (A)`、`if (B)` | A、B 各取真和假，尽量一次同时覆盖 | 不必机械枚举四种组合 |
| `A && B` | F／跳过；T/F；T/T | A 假时 B 没执行，不能说"B 测过假" |
| `A \|\| B` | T／跳过；F/T；F/F | A 真时 B 没执行 |
| `A && B && C` | F；T/F；T/T/F；T/T/T | 通常 4 条短路路线，不是 8 次 |
| `A \|\| B \|\| C` | T；F/T；F/F/T；F/F/F | 只有前面都假才执行 C |
| `switch` | 每个可达 `case`、可达 `default`，留意贯穿 | 枚举值不一定能走到 default |
| 提前 `return` / `throw` | 前面没退出才能到达后面的条件 | 一次调用不会经过两个互斥出口 |

短路那几行对应的是"**把短路展开**"的口径。若题目只要求完整判定真/假，别机械套 3 次或 4 次；条件之间有关联时还要剔除走不通的组合。

## T9｜异常测试：三种写法选一种

### T9-A：JUnit 4 `expected`（一个方法只触发一次异常）

**粘贴位置**：测试类内，不能写在别的方法里面。

```java

}
```

**别在后面追第二个非法输入**：第一处抛出后方法立即结束，第二行永远不执行。也不要在这个方法里 `try/catch` 把异常吞掉。

### T9-B：JUnit 4 通用 `try/catch + fail`（需要查消息时用）

**粘贴位置**：已有普通 `@Test` 方法内；**不要**同时给这个方法加 `expected`。

```java

    Target.calculate(-1);

    // 没抛异常就必须失败，否则测试会假通过
    fail("应抛 IllegalArgumentException");
} catch (IllegalArgumentException ex) {
    // 只有题目明确要求检查消息时，才保留下面这行
    assertEquals("quantity must be non-negative", ex.getMessage());

```

只捕获指定的异常类型，别写 `catch (Throwable)`——它会把 `fail()` 抛的 `AssertionError` 一起吞掉，测试反而全绿。

```java
// assertEquals("...", ex.getMessage());
```

`assertThrows` 和 JUnit 4 的 `expected` 都接受**指定异常的子类**；只有要求精确类型时才额外查 `ex.getClass()`。

### T9-D：2022 S1 State 原题两块

## T11｜黑盒测试：正常值、边界值、特殊规则、非法值

### T11-A：把规格翻成输入表

| 规格 | 候选输入 | 期望怎么定 |
|---|---|---|
| 合法闭区间 `[L,U]` | L−1、L、L+1、U−1、U、U+1 | 合法值按公式算；越界按约定抛异常或返回值 |
| `< k` / `<= k` / `>= k` | k−1、k、k+1 | 等于门槛才能区分 `<` 与 `<=` |
| 整数除法 `q / d` | d−1、d、d+1、2d | 例：`5/6=0`、`6/6=1` |
| 名单匹配 | 名单内、名单外；大小写按规格 | 不要假设允许 null |
| `null` / `""` / `" "` | 三种分别考虑 | trim 会把空白串变空，但 null 不能 trim |
| 只处理前 n 个字符 | 长度 n−1、n、n+1；第 n+1 位放有效字符 | 分清"前 n 个位置"还是"前 n 个有效字符" |
| 大小写敏感 / 仅字母 | `"A"`、`"a"`、`"1A!"` | 按字符规则手算 |
| 特例优先 | 特例、紧邻特例的普通值 | 先套特例，别用普通公式覆盖它 |

这张表是**选材库**，最少覆盖题不要全塞进去。多实现题要用框架给你的对象，别自己 `new` 某个固定实现。正确版本应全通过，错误版本至少失败一条；但有限样例保证不了识别未来所有错误实现。

**一处已知冲突**：README 说合法 size 是 1–31，仓库基类却只检查 `<0`。所以 size=0 按文字该抛异常，但会让某些共享基类的实现失败。这里保留该用例并标明来源，但不能保证未知评分器也这么认。

## T12｜2024 S1 AVL：`data()` 与 `createTree()` 要成对改

**先读约束**：这题要求最少的是所有测试树的**总节点数**；不测空树、null、重复值；只给原方法评分。下面是四种基本旋转的模板（共 12 个节点），**不是已证明的全题最优解**，也识别不了所有错误实现。

### T12-A：替换 `data()` 的 return

```java
// ← 整段替换 data() 里的 return
return java.util.Arrays.asList(new Object[][] {

    // 插入 30,20,10 → LL 旋转，前序 20 10 30
    {0, java.util.Arrays.asList(20, 10, 30)},

    // 插入 10,20,30 → RR 旋转
    {1, java.util.Arrays.asList(20, 10, 30)},

    // 插入 30,10,20 → LR 旋转
    {2, java.util.Arrays.asList(20, 10, 30)},

    // 插入 10,30,20 → RL 旋转
    {3, java.util.Arrays.asList(20, 10, 30)}
});
```

### T12-B：替换 `createTree(int treeIdentifier)` 的方法体

```java
int[][] values = {
    {30, 20, 10},
    {10, 20, 30},
    {30, 10, 20},
    {10, 30, 20}
};

// 用 data() 里的那一列做下标，两边必须对得上
int[] row = values[treeIdentifier];
AVLTree tree = createTreeNode(row[0]);

for (int i = 1; i < row.length; i++) {
    // 旋转可能换根，必须接住返回值
```

## T13｜BST 递归测试：小树覆盖左右方向和终止条件

**可直接对应**：练习 `misc-questions/q6-bst-testing/BST.java` 的 `find(Node, Integer)`。别的年份若参数顺序、构造器或返回类型不同，先改接口。

**粘贴位置**：JUnit 4 测试方法体；需要静态断言 import。

```java
BST tree = new BST();

// 空树：n == null 终止
assertNull(tree.find(tree.root, 10));

// 建一棵小树：10 为根，5 在左，15 在右
tree.insert(10, 'A');
tree.insert(5, 'C');
tree.insert(15, 'G');

// key 为 null：用非空树才能走到第二个判断
assertNull(tree.find(tree.root, null));

// 相等：返回当前节点
assertSame(tree.root, tree.find(tree.root, 10));

// 小于：向左递归后找到
assertSame(tree.root.left, tree.find(tree.root, 5));

// 大于：向右递归后找到
assertSame(tree.root.right, tree.find(tree.root, 15));

// 走入空子树：找不到
assertNull(tree.find(tree.root, 6));
```

这组把场景分得很清楚。若题目要求**最少**，空树用例和最后"找不到"都覆盖 `n == null`，可以按总覆盖合并。

## T14｜最少用例证明、选择题和交卷纠错

### “最少”不是删到不能删就证明全局最少

先列所有目标分支，给每条用例标出覆盖集合；没有新增覆盖的先删。**这只能找到一个不可再删的集合，不必然是全局最小集合。**再找下界：例如 3 个互斥 return 至少 3 次；一个互斥出口内部还要覆盖三种短路走法，就把这三次计入。构造出的组数达到下界，才有最少证明。有关联的条件、循环、辅助方法范围都会影响下界。

| 原题 / 场景 | 数什么 |
|---|---|
| 2025 S2 Pricing | `data()` 的数据组；不能用一行包装内部多次调用绕过 |
| 2021 S2 findSomething | 被测方法调用次数；只有一条 assert 也可能调用两次 |
| 2020 S2 Person / Repository | 断言执行次数；循环执行 N 次就数 N 次，异常测试也须按题意处理 |
| 2024 S1 AVL | 所有测试树总节点数；不是只数树或测试方法 |
| 黑盒多实现 | 通常要求识别实现，不等于最少分支覆盖题 |

### 概念速查

| 概念 | 考场判断 |
|---|---|
| 语句覆盖 | 每个要求的可执行语句执行过；不一定测 if 的假出口 |
| 分支覆盖 | 每个可达判断方向走过；课程题可能把短路也展开 |
| 条件覆盖 | 每个基本条件实际被求值时出现真、假 |
| 路径覆盖 | 从入口到出口的完整路径；循环可产生无穷多路径 |
| 包含关系 | 通常同一可达范围下：100% 路径 ⇒ 100% 分支 ⇒ 100% 语句；反向不保证 |
| 百分比 | 70% 路径不能推出至少70%分支，分母不同 |
| 条件与完整判定 | 条件全真/假不自动保证完整判定两种结果；完整判定两种结果也不保证每个子条件两种结果 |
| 独立判断链 | 路径数可能相乘；最少分支用例可能组合覆盖。例如独立4路和5路，全部组合可行时20条路径、5组可覆盖各出口 |
| 等价类 / 边界值 | 每类挑代表，再测门槛前/等于/后；期望来自规格 |
| 回归测试 | 修改后重跑旧测试，检查已有行为有没有被破坏 |
| 测试 / 调试 | 测试发现不符合预期；调试定位并修复原因 |
| 全绿 / 高覆盖 | 不等于证明所有输入都正确；断言也可能写错 |

**JUnit 最后核对：**expected 在左、actual 在右；double 加误差；Integer 重载明确；数组用 assertArrayEquals；JUnit4 测试 public void 非 static 无参数；data public static；参数列/下标匹配；异常后面不会继续执行；`timeout=1000` 是毫秒不是循环次数；`throws X` 仅允许异常传出，**不表示期望 X**；不写空 catch 吞掉任意异常；不把被测输出再抄作 expected；修复阶乘示例时 `0!=1`、`5!=120`、`6!=720`，不要颠倒期望值。

# 原有讲解（以下内容保留）

# 02｜测试：每个用例为什么存在

> 写测试先确定输入和期望结果，再看题目要求覆盖代码路径，还是核对文字规格；“一个用例”怎样计数，以原题为准。

## 1. 认题型：拿到题后照着做

先别背“白盒”“黑盒”这些词。把题目的要求翻译成：**我要给方法什么输入？它应该返回什么？我为什么需要这一组输入？**下面从一段能手算的代码开始。

### 情况 A：题目写 `branch complete`

**它是什么意思？**`branch` 是“分支”，指程序遇到一个判断后可能走的不同方向。例如 `if (x > 0)` 有两条路：条件成立，走进 `if`；条件不成立，跳过 `if`。`complete` 是“覆盖完整”。因此 **branch complete（分支覆盖完整）**就是：每条能走的判断方向，至少用一组输入走过一次。测试全部显示通过，也不代表所有方向都走到了。因为要看源码里的判断，这属于**白盒测试**：“盒子”里的代码是看得见的。

题目若还写 **minimum**，意思是“在完成覆盖的前提下，使用最少的用例”；它不是另一种覆盖类型。

假设原题给了这个方法，让你测试它：

```java
static int sign(int x) {
    if (x > 0) {        // 问：x 是否大于 0？
        return 1;       // 回答“是”才走到这里
    }
    return 0;           // 回答“否”才走到这里
}
```

`x` 是你传进去的数字；`return` 是方法给你的结果。把输入**一行一行代入**：

1. 传 `x=5`：`5 > 0` 是真，执行 `return 1`。所以期望结果是 `1`。
2. 传 `x=0`：`0 > 0` 是假，跳过花括号，执行 `return 0`。所以期望结果是 `0`。

测试可以写成：

```java
assertEquals(1, sign(5)); // 期望 1；实际调用 sign(5)；覆盖“真”
assertEquals(0, sign(0)); // 期望 0；实际调用 sign(0)；覆盖“假”
```

这就叫**分支覆盖**：同一个 `if` 问题，回答“是”和“否”的路各走一次。只测 `5`，即使测试通过，仍没有检查“否”这条路。

如果题目还写 `minimum`（最少），这两组已经够了。再加 `sign(8)` 只会重复走“真”，用例变多但没有覆盖新路。**先找到所有需要走的路，再删去只重复旧路的输入。**遇到多个 `if` 或 `&&`、`||` 时，照第 3 节逐个画真 / 假格子；一个输入可能同时覆盖多个格子。

### 情况 B：题目写 `statement coverage` 或 `code complete`

**它是什么意思？**`statement` 是“语句”，就是程序实际执行的动作，例如“把 `x` 加 1”或“返回 `x`”。**statement coverage（语句覆盖）**要求目标语句都至少执行一次。它只问“这句有没有执行过”，不要求每个判断的真、假方向都试过。本手册涉及的历年题中，`code complete` 也按这个语句覆盖要求处理；做新题仍要先读原题的具体定义。

换成这段代码：

```java
static int plusOneIfPositive(int x) {
    if (x > 0) {
        x = x + 1;      // 语句①
    }
    return x;           // 语句②
}
```

如果只要求**语句覆盖**，传 `x=5`：条件是真，语句①把 `5` 改成 `6`，语句②返回 `6`。一次调用就执行了这两条语句：

```java
assertEquals(6, plusOneIfPositive(5));
```

这里不用再传 `0`，因为题目只要求“每条语句执行过”，没有要求 `if` 的真、假两条路都走过。如果同一段代码改问 **branch complete**，就还要加 `assertEquals(0, plusOneIfPositive(0))`，专门走“假”路。**先看题目问的是“语句”还是“分支”，答案可能不同。**

### 情况 C：题目给多个实现，要求正确版通过、错误版失败

**它是什么意思？**“实现”（implementation）指同一个功能的**不同代码版本**：对外的方法一样，内部写法不同，其中一部分是正确的，一部分被故意改坏。题目给你一批这样的版本，让你写一份测试；评分时把你的测试分别跑在每一个版本上——正确版本必须全部通过，错误版本至少要有一条失败。这类题通常叫**黑盒测试**，原因见本节末尾。

**先用一段能手算的规则看结构。**README 写：“订单金额达到 100 元，运费为 0；不足 100 元，运费为 10 元。”按文字算出两个期望值，写成两条断言：

```java
assertEquals(10, shipping(99));  // 99 不到 100，应付 10
assertEquals(0, shipping(100));  // 100 已达到门槛，应付 0
```

假设题目给了四个版本的 `shipping`，评分时每一版都要跑这两条：

| 版本 | 内部条件 | `shipping(99)` 期望 10 | `shipping(100)` 期望 0 | 该版本跑完 | 应判 |
|---|---|---|---|---|---|
| 正确版 | `amount >= 100` | 10，通过 | 0，通过 | 全部通过 | 正确 |
| 错误甲 | `amount > 100` | 10，通过 | 10，**失败** | 一条失败 | 错误 |
| 错误乙 | `amount >= 90` | 0，**失败** | 0，通过 | 一条失败 | 错误 |
| 错误丙 | 一律返回 0 | 0，**失败** | 0，**失败** | 两条都失败 | 错误 |

“至少有一条失败”里的“至少”就在这张表里：错误甲只失败一条，照样算被抓到，不需要每条都失败。反过来，若某个错误版本在你的**所有**断言上全部通过，说明你没抓到它，要扣分。`99` 和 `100` 也不是随便选的：它们卡在“达到”与“超过”的分界上，只测其中一个，错误甲或错误乙就会漏过去。

**再看它在文件里长什么样。**以 [2024 S2 Q2](../exam-practice-questions/past-exams/2024-2/src/Q2/Q2README.md) 为例：

```
Q2/HashingBox.java                        抽象父类，定义 hash(Thing) 这个功能
Q2/HashingBox0.java ~ HashingBox12.java   13 个版本，都实现同一个 hash
Q2/Q2Test.java                            唯一要交的文件
```

13 个类对外提供同一个 `hash(Thing)`，从调用方看不出区别；README 说明其中有 1～3 个是正确的。评分程序把你的 `Q2Test` 跑 13 遍，每遍换一个版本，于是得到 13 个结果：

| 某个版本跑完的结果 | 等于你判定它 |
|---|---|
| 全部通过 | 正确 |
| 至少一条失败 | 错误 |

13 个版本全部判对才有满分。所以你要做的是：**让正确版本全绿，让每个错误版本至少红一条。**

**为什么不能从代码里抄答案。**13 份代码里有对有错，你事先并不知道哪份对。若拿 `HashingBox3` 跑出的数字当期望值，而它恰好是错的，你就把错误答案写进了断言，正确版本反而变红。原题写明：把正确版本判错，比放过一个错误版本扣得更多。期望值只有一个来源——**README 的文字规则加自己手算**。

**这就是黑盒。**“盒子”指被测代码。白盒是打开盒子，照着 `if`、循环设计输入（情况 A、B 的做法）；黑盒是不打开盒子，只从外面喂输入、看输出，按说明书判对错。13 个盒子没法逐个打开读，所以 2024 S2 Q2 直接写 *STRONGLY ADVISED to perform Black Box Testing*。

**这类题的动手顺序。**

1. 把 README 的规则抄成短句，圈出“怪规则”。2024 S2 有三个：`size == 1` 时 `sizeHash` 是 `2`（不是 1）；`nameHash` 只算前 6 个字符、且只算字母；`size` 越界要抛 `ComponentOutOfRangeException`。错误版本往往就栽在这些地方。
2. 每条规则配一个**最小可区分输入**：这条规则被写错时，结果一定会跟着变。
3. 手算期望值，写成断言，每条注明“它查的是哪条规则”。
4. 刻意挑边界：`size` 取 `1`、`2`、`31`、`32`；名字取正好 6 个字符和 7 个字符；名字里混数字、空格；material 与 shape 取两端值。
5. 断言写完后回头自查：有没有哪个版本可能所有断言都通过？有，就补一条。

### 情况 D：题目明确要求某种异常

**它是什么意思？**“异常”是程序遇到不允许的情况时发出的错误信号，例如商品数量传了负数。题目若说“负数数量要抛 `IllegalArgumentException`”，测试就要确认：传入负数时，方法确实发出这个指定类型的错误信号，而不是正常返回一个结果。

待测的是一个**“输入负数会抛异常”的计算器**：每件商品 10 元，**数量为负就报错**。我们要写的**测试，就是验证它拿到负数时确实会抛**，而不是照常返回一个价格。实现如下：

```java
static int calculatePrice(int quantity) {
    if (quantity < 0) {
        throw new IllegalArgumentException();
    }
    return quantity * 10;
}
```

三处要点：`if (quantity < 0)` 判断参数是否非法；`throw` 是主动抛出；`IllegalArgumentException` 是“非法参数”异常，表示传进来的参数不合规。于是：

| 调用 | 行为 |
|---|---|
| `calculatePrice(3)` | 正常返回 `30` |
| `calculatePrice(-1)` | 抛出 `IllegalArgumentException` |

**如何实现测试抛出异常。**JUnit 4 把期望写在注解属性里：

```java
@Test(expected = IllegalArgumentException.class)
public void negativeQuantityThrows() {
    calculatePrice(-1);
}
```

- `@Test`：告诉 JUnit 这是一条测试。
- `expected = IllegalArgumentException.class`：整句意思是“本方法必须抛出 `IllegalArgumentException` 才算通过”。传的是类型，所以要写 `.class`，不是 `new IllegalArgumentException()`。
- `calculatePrice(-1)`：故意传非法值。方法体里不写 `try/catch`——异常要抛出来给 JUnit 看见，自己吞掉就等于“正常返回”，测试反而失败。
- 方法名 `negativeQuantityThrows` = “负数数量会抛异常”。名字不影响判定，只影响可读性。

**什么情况下通过。**

| 实际行为 | 结果 | 原因 |
|---|---|---|
| 抛出 `IllegalArgumentException` | 通过 | 符合规格 |
| 返回 `-10` | 失败 | 该抛没抛 |
| 返回 `0` | 失败 | 该抛没抛 |
| 抛出 `NullPointerException` | 失败 | 异常类型不对 |

**反直觉但常考：抛异常不等于测试失败。**规格要求抛异常时，抛出正确类型恰恰是通过条件；真正让测试失败的是“该抛没抛”。

**两种 `expected` 不要混。**普通变量 `expected` 只表示期望的返回值：

```java
int expected = 30;
int actual = calculatePrice(3);
assertEquals(expected, actual);
```

而 `@Test(expected = X.class)` 里的 `expected` 是注解属性，表示期望的**异常类型**。看到 `expected` 这个词不能判定是异常题，要看它出现在哪。

**速记。**

| 写法 | 含义 |
|---|---|
| `throw` | 抛出异常 |
| `new IllegalArgumentException()` | 创建非法参数异常对象 |
| `@Test` | 声明测试方法 |
| `expected = X.class` | 期望抛出 X 类型异常 |
| `assertEquals(a, b)` | 检查实际值是否等于期望值 |

一句话：`@Test(expected = X.class)` = 不抛失败、抛错类型失败、抛对类型才通过。若题目还要求检查异常消息，这个注解不够用，要改成 `try/catch` 加 `fail()`。JUnit 5 的等价写法是 `assertThrows(IllegalArgumentException.class, () -> calculatePrice(-1))`，本课程仍用 JUnit 4。

### 最后看“一个用例”怎样计数

**“用例”是什么？**可以先把它想成“一次有目的的检查”：给方法一组输入，事先确定应该发生什么，再运行并检查结果。但考试的**计数规则**可能不同：有的数数据行，有的数断言执行次数，有的数方法调用次数。所以“写在同一个测试方法里”不表示只算一个。

**一个 `@Test` 不一定等于一个用例。**拿下面这个方法举例：

```java
static int sign(int x) {
    if (x > 0) return 1;
    if (x < 0) return -1;
    return 0;
}
```

| 输入 `x` | 期望 | 为什么 |
|---|---|---|
| `5` | `1` | 正数 |
| `-3` | `-1` | 负数 |
| `0` | `0` | 零 |

三组“输入 + 期望”就是 3 个用例。但如果只写成：

```java
@Test
public void testSign() {
    assertEquals(1, sign(5));
    assertEquals(0, sign(0));
}
```

整个类只有一个 `@Test`，却检查了两组不同输入：2 次断言、2 次调用。**到底算几个，取决于题目口径，不是 Java 规定的。**

**三种口径。**先在原题 README 中找 *test case*、*assertion*、*invocation*、*minimum*：

| 题目出现 | 数什么 |
|---|---|
| 按数据行数（`data()`、*test case*） | 有几组“输入、期望” |
| 按断言次数（*assertion*） | `assertEquals` 等断言执行了几次 |
| 按方法调用次数（*invocation*） | 被测方法被调了几次 |

**口径一：按数据行数。**参数化测试的 `data()` 里放几行，就是几组：

```java
@Parameters
public static Collection<Object[]> data() {
    return Arrays.asList(new Object[][] {
        {5, 1},
        {0, 0}
    });
}
```

`{5, 1}` 是“输入 5、期望 1”，`{0, 0}` 是“输入 0、期望 0”，两行就是 **2 个用例**，即使整类只有一个 `@Test` 方法也是如此。[2025 S2 Q2](../exam-practice-questions/past-exams/2025-2/src/Q2/Q2README.md)要求 `data()` 放最少用例，多一行或少一行都会扣分。

**口径二：按断言次数。**同一个 `test()` 中执行 `assertEquals(1, sign(5))` 和 `assertEquals(0, sign(0))`，是 **2 次断言、2 个用例**。[2020 S2 Q2](../exam-practice-questions/past-exams/2020-2/Q2/README.md)明确采用这个口径。

**口径三：按被测方法调用次数。**下面这段最容易数错，因为它只有一条断言：

```java
@Test
public void test() {
    int a = sign(5);
    int b = sign(0);
    assertEquals(1, a);
}
```

| 数什么 | 数量 |
|---|---|
| `@Test` 方法 | 1 |
| `sign()` 调用 | 2 |
| `assertEquals()` 执行 | 1 |

哪怕 `sign(0)` 的结果没被断言，它也是一次调用，按调用口径就是 **2 个用例**。[2021 S2 Q1](../exam-practice-questions/past-exams/2021-2/q1/readme.md)明确采用这个口径。

**两个会改变计数的细节。**`for` 循环里的一行断言，执行几次就算几次；JUnit 4 在第一条断言失败处就终止该方法，后面的断言不会执行，实际计数可能少于写下的条数。

记住答题顺序：**读要求 → 代入输入手算期望 → 说明这一组覆盖了哪条路或哪条规则 → 按原题口径数用例。**

## 2. 读懂断言

```java
assertEquals(12, Pricing.calculatePrice(3, 4, "id1"));
```

左边是**预先算出的期望**，右边是实际结果。`assertTrue` / `assertFalse` 检查布尔值；`assertSame` 检查是否同一个对象。对象类型需与 JUnit 重载匹配，必要时用 `Integer.valueOf(12)` 或对实际 `Integer` 调 `.intValue()`。

## 3. 分支覆盖：画真 / 假表

```java
if (a < 0 || b < 0) return 1;
return 0;
```

本课程相关题目把 `&&`、`||` 的子条件也计入分支。`||` 会短路：`a<0` 为真时，`b<0` 不执行。

| 输入 (a,b) | a<0 | b<0 | 返回 |
|---|---|---|---|
| (-1,0) | 真 | 未执行 | 1 |
| (0,-1) | 假 | 真 | 1 |
| (0,0) | 假 | 假 | 0 |

这三行让两个子条件的真、假都出现。最少用例的做法是：

1. 列出每个判断和短路子条件。
2. 每个条件画“真 / 假”两格。
3. 从难到达的格子倒推输入；让同一输入顺便覆盖别的格子。
4. 手算每行期望值。
5. 删除没有新增覆盖的行，再检查是否仍全部覆盖。

一次调用可经过多个条件，所以**出口数不等于最少用例数**。

## 4. 白盒与黑盒的区别

白盒看已有代码路径。代码逻辑即使古怪，也按原题实现计算期望。2025 S2 Pricing 的七组输入分别覆盖空数量、空会员、数量 4 的中间路径、会员名单、单价门槛和整数除法。详细覆盖矩阵见[原稿 2025 S2 小节](../其他/零基础快速掌握手册/原稿归档/02-testing.md#41-2025-s2-q2-pricing-最少分支覆盖)。

黑盒从 README 的**规格**算期望。把正常情况、边界、无效输入列成表；不能运行某个待测实现后把它的输出抄为正确答案，因为它可能是错误版本。

## 5. JUnit 4 的两种常见写法

### 参数化测试：一个 `@Test` 跑 N 组数据

核心：JUnit 用**每组数据新建一个对象**，再运行那条测试。

```java
@RunWith(Parameterized.class)
public class SignTest {

    @Parameters                                 // ① 数据来源
    public static Collection<Object[]> data() {
        return Arrays.asList(new Object[][] {
            {5, 1},
            {0, 0}
        });
    }

    int input;                                  // ② 成员变量
    int expected;

    public SignTest(int input, int expected) {  // ③ 构造器：每组参数轮流传入
        this.input = input;
        this.expected = expected;
    }

    @Test
    public void testSign() {                    // ④ 每个对象跑一次
        assertEquals(expected, sign(input));
    }
}
```

JUnit 把 `data()` 的每一行**按列顺序轮流传给构造器**：第一列进第一个参数，第二列进第二个参数，一行造一个对象。

各部分的职责：

| 代码 | 作用 |
|---|---|
| `@RunWith(Parameterized.class)` | 开启参数化，让 JUnit 用下面的数据表驱动测试 |
| `@Parameters` | 标记 `data()` 是数据来源 |
| `data()` | 返回所有“输入 + 期望”的行 |
| `Collection<Object[]>` | 一行就是一个 `Object[]` |
| `int input; int expected;` | 存放当前这行的参数 |
| 构造器 | 接住轮流传入的一组参数，存进对象 |
| `@Test` | 真正的测试，只有一份 |
| `assertEquals` | 用当前这行的期望值比较 |

JUnit 内部相当于：

```java
SignTest t1 = new SignTest(5, 1);  t1.testSign();
SignTest t2 = new SignTest(0, 0);  t2.testSign();
```

| 第一组数据 | 第二组数据 |
|---|---|
| `input = 5` | `input = 0` |
| `expected = 1` | `expected = 0` |
| `assertEquals(1, sign(5))` | `assertEquals(0, sign(0))` |

考试口径：**1 个 `@Test` + 2 组参数 = 2 次执行、2 个用例**。流程是 `data()` → 读一行 → 调构造器 → 存成员变量 → 跑 `@Test` → 读下一行。每组参数创建的都是**新对象**，不是在同一个对象上改字段。

考试时骨架通常已给，你只填 `data()`；每行的列顺序要和构造器参数（或 `@Parameter(0)` 字段）一致。

### 异常测试

检查一次异常：

```java
@Test(expected = IllegalArgumentException.class)
public void rejectsNegativeQuantity() {
    Calc.price(3, -1);
}
```

异常类要用题目指定的具体类型。语句覆盖题还要分别执行每个目标 `throw`、`return`，但不一定需要每个判断的真、假都走到。

#### 题目（原题内容）

**已给代码：`Pricing.java`（原文件）**

```java
import java.util.*;


public class Pricing {
    int unitPrice;
    Integer quantity;
    String memberId;

    public Pricing(int unitPrice, Integer quantity, String memberId) {
        this.unitPrice = unitPrice;
        this.quantity = quantity;
        this.memberId = memberId;
    }


    /**
     * Calculate the price of a mysterious object under a mysterious pricing scheme.
     */
    public static Integer calculatePrice(int unitPrice, Integer quantity, String memberId) {
        double discount = 0.0;

        if (quantity == null) {
            discount -= 0.2;
            quantity = 1;

            if ((memberId == null || memberId.trim().isEmpty())) {
                discount -= 0.1;
            }
        }

        if (quantity <= 3) {
            return unitPrice * 4;
        }
        else if (quantity >= 5) {
            if (List.of("id1", "id2", "id3").contains(memberId) && unitPrice >= 3) {
                return 10;
            } else if (quantity / 6 >= 1) {
                quantity -= quantity / 6;
            }
        }
        
        return (int) (unitPrice * quantity * (1 - Math.min(discount, 0)));
    }


}
```

#### 逐步讲解与做题套路


原题：[题目说明](../exam-practice-questions/past-exams/2025-2/src/Q2/Q2README.md) · [Pricing.java](../exam-practice-questions/past-exams/2025-2/src/Q2/Pricing.java) · [测试骨架](../exam-practice-questions/past-exams/2025-2/src/Q2/CalculatePriceTest.java)。

**题目要什么？** 只在 `data()` 填参数化测试数据，用尽量少的调用覆盖分支。不能写会抛异常的用例；即使计价方式奇怪，也必须按给定代码计算。

**第一步：把控制流翻译成人话。**

```text
quantity 是 null？
    是：discount 减 0.2，把 quantity 改成 1
        memberId 是 null 或去空白后为空？是则 discount 再减 0.1
quantity <= 3？是就立即返回 unitPrice * 4
否则 quantity >= 5？
    是：会员在名单里且 unitPrice >= 3？是就返回 10
        否则 quantity / 6 >= 1？是就把数量减去 quantity / 6
最后按公式计算并转换为 int
```

`return` 后不会继续往下执行。`quantity / 6` 是整数除法：`5 / 6 = 0`，`6 / 6 = 1`。

**第二步：把短路也画进控制流。** `A || B` 在 A 为真时不算 B；`A && B` 在 A 为假时不算 B。按照把这些短路判断也分别覆盖的口径，可以用下面 **7 组**：

| 编号 | unitPrice | quantity | memberId | 期望值 | 主要补上的路径 |
|---|---:|---|---|---:|---|
| 1 | 3 | `null` | `null` | 12 | 第一个 OR 左边为真，右边跳过 |
| 2 | 3 | `null` | `" "` | 12 | OR 左边假、右边真 |
| 3 | 3 | `null` | `"id1"` | 12 | OR 左边假、右边假 |
| 4 | 3 | 4 | `"other"` | 12 | `<=3` 假，`>=5` 也假 |
| 5 | 3 | 5 | `"id1"` | 10 | 名单匹配且价格达标，提前返回 |
| 6 | 3 | 5 | `"other"` | 15 | 名单不匹配；`5/6>=1` 为假 |
| 7 | 2 | 6 | `"id1"` | 10 | 名单匹配但价格不达标；`6/6>=1` 为真 |

**第三步：不要猜价格，逐行算。**

- 第 1–3 组：quantity 原来是 null，进入首段后变成 1。随后 `1 <= 3` 成立，直接返回 `3×4=12`。discount 虽然变了，却没机会进入最后公式。
- 第 4 组：quantity=4，两个数量条件都不成立；discount=0，结果为 `3×4×(1−0)=12`。
- 第 5 组：直接命中会员条件，返回 10。
- 第 6 组：不属于会员，`5/6=0`，数量不减，返回 `3×5=15`。
- 第 7 组：价格 2 不达标，进入数量调整，`6−6/6=5`，返回 `2×5=10`。

放进原来的 `data()` 返回语句中：

```java
return Arrays.asList(new Object[][]{
    {new Pricing(3, null, null), 12},
    {new Pricing(3, null, " "), 12},
    {new Pricing(3, null, "id1"), 12},
    {new Pricing(3, 4, "other"), 12},
    {new Pricing(3, 5, "id1"), 10},
    {new Pricing(3, 5, "other"), 15},
    {new Pricing(2, 6, "id1"), 10}
});
```

**为什么这一口径下不能少？** 首段 OR 的三种短路走法需要 3 次 quantity=null，而这 3 次都会在 `<=3` 返回；quantity=4 的路径另需 1 次；后段会员 AND 的三种走法另需 3 次。至少 `3+1+3=7`，表中正好实现。

**计数口径要分清：** 原题没有在文字里进一步定义是否把短路内部单独计分。如果只把每个完整 `if` 条件视为一个判定，不拆 `||` / `&&`，删去第 2 组后 6 组就够。上面的 7 组结论明确针对含短路的控制流口径，不把它冒充已公布的评分答案。

**做题套路：先找提前 return → 分开互斥路径 → 为短路判断造真/假 → 手算 expected → 证明数量下界。** 不要为了试 null，给 quantity≥5 的用例随意传 null memberId：这里 `List.of(...).contains(null)` 可能抛异常，违反原题限制。

> 1) The `sizeHash` is the largest prime number not larger than the `size` of the Thing,
>    with an exception where the sizeHash for a Thing with size==1 is *2*.
>    - E.g., the `sizeHash` of 6 is 5. 
>    - E.g., the `sizeHash` of 3 is 3.
>
> 2) The `nameHash` computes a hash for a given string (name) by summing the
>    product of each letter's ASCII value (considering only the first 6 characters
>    for the ASCII-sum) and multiplying it by the specified `sizeHash`, then 
>    adding to it the length of the name.
>   - Note that only alphabetic characters (English letters) are included in the ASCII-sum.
>   - E.g., if sizeHash==3, the `nameHash` of "Comp2100" is
>     `<ASCII-sum for letters in the first 6 characters> * <sizeHash> + <length of name> =`
>     `(67 + 111 + 109 + 112) * 3 + 8 = 1205`
>   - E.g., if sizeHash==1, the `nameHash` of "1aaaa1aaaa" is
>     `(97 x 4) * 1 + 10 = 398`
>
> 3) The `materialSizeHash` is the product of the **values** of the `material`
>    and `shape` of the Thing.
>    - E.g., a Square-shaped Silver will have a materialSizeHash of `925 x 4 = 3700`
>
> 4) Finally, the overall `hash` value is the sum of `nameHash` and `materialShapeHash`.
>    - Note that when the `size` of a Thing instance is out of bound, `hash` is expected 
>      to throw a `ComponentOutOfRangeException`.

```java
package Q1;

import java.util.Arrays;

public class Riddle {
    public enum RiddleType {
        TEXT_RIDDLE,
        NUMERIC_RIDDLE,
        ANAGRAM_RIDDLE;
    }

    private String question;
    private String answer;
    private boolean isSolved;
    private RiddleType type;

    public Riddle(String question, String answer, RiddleType type) {
        this.question = question;
        this.answer = answer;
        this.isSolved = false;
        this.type = type;
    }

    public String askQuestion() {
		return this.question;
    }

    public boolean checkAnswer(String input) {
        boolean isCorrect = false;

        if (type == RiddleType.TEXT_RIDDLE) {
            if (input.equalsIgnoreCase(answer)) {
                isCorrect = true;
            }
        } else if (type == RiddleType.NUMERIC_RIDDLE) {
            if (input.matches("\\d+") && Integer.parseInt(input) == Integer.parseInt(answer)) {
                isCorrect = true;
            }
        } else if (type == RiddleType.ANAGRAM_RIDDLE) {
            char[] inputChars = input.toLowerCase().toCharArray();
            char[] answerChars = answer.toLowerCase().toCharArray();
            Arrays.sort(inputChars);
            Arrays.sort(answerChars);
            if (Arrays.equals(inputChars, answerChars)) {
                isCorrect = true;
            }
        }

        if (isCorrect) {
            isSolved = true;
        }
        return isCorrect;
    }

    public boolean isSolved() {
		return isSolved;
    }

    public void setSolved() { isSolved = true; }

    public String getAnswer() {
        return answer;
    }
}
```

#### 逐步讲解与做题套路


原题：[说明](../exam-practice-questions/past-exams/2021-2/q1/readme.md) · [BranchComplete.java](../exam-practice-questions/past-exams/2021-2/q1/BranchComplete.java)。

原代码：

```java
if (a < 0 || b < 0) {
    return a < b || a > c;
}
return a < b && a > c;
```

**题目要什么？** 最少的分支覆盖测试；每调用一次 `findSomething` 算一组，不是每个 `@Test` 才算一组。

按短路控制流展开后，可以用以下 6 组：

| a,b,c | 外层走向 | 内层怎么计算 | 结果 |
|---|---|---|---|
| −2,−1,0 | a<0 真，不再算 b<0 | a<b 真，OR 直接成立 | true |
| 1,−1,0 | a<0 假，b<0 真 | a<b 假，a>c 真 | true |
| −1,−2,0 | a<0 真 | a<b 假，a>c 假 | false |
| 2,1,0 | 两者都非负 | a<b 假，AND 直接失败 | false |
| 1,2,0 | 两者都非负 | a<b 真，a>c 真 | true |
| 1,2,3 | 两者都非负 | a<b 真，a>c 假 | false |

**以第二行为例逐步代入：** `1<0` 假，所以继续算 `−1<0`，是真；进入上面的 return。`1<−1` 假，所以继续算 `1>0`，为真，最终返回 true。

上面 return 的 OR 有三种短路走法，下面 return 的 AND 也有三种；一次调用只能进入其中一个 return，所以这一口径下至少需要 6 次。表中也顺便覆盖了外层 OR 的所有短路走法。

**做题套路：把每个复合条件拆成实际会执行的比较 → 给每条 return 分配输入 → 标明“未执行”而不只是 true/false → 合并重复覆盖。** 若课程仅按完整 if 判定计分，则需按该定义重新计算，不能脱离定义背“6”。
