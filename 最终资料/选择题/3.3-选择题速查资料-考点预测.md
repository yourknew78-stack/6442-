## 1. 软件构建基本概念

**已考定位：**往年 2024 S1 MCQ1。

### 1.1 定义与分类

Software construction（软件构建）是把设计落实为可运行软件的活动，核心包括编码、详细设计、单元测试和调试。它不是软件工程全部活动的同义词。

| 英文 | 中文与具体含义 | 选择题判断 |
|---|---|---|
| Coding / implementation | 写出实现功能的代码 | 构建的核心 |
| Detailed / modular design | 决定模块内部结构、函数和接口怎样实现 | 与构建密切相关；别把所有 design 都排除 |
| Unit testing | 检验小单元是否按预期工作 | 属于构建相关活动；testing 不只有独立测试团队做 |
| Debugging | 定位错误原因并修改 | 与 testing 不同：测试发现问题，调试解释并修复 |
| Readability | 通过命名、结构和注释让代码可读 | 是构建质量考虑 |
| Coding standards | 团队共同遵守编码规则 | 支持构建，不只是美观 |
| IDE / profiler | 编写、运行、调试与测量代码的工具 | 属于构建工具语境 |
| Problem definition / requirements | 确定要解决什么问题、需要什么功能 | 通常属于需求活动，不是狭义构建 |
| Project planning | 排期、预算、人员分配 | 通常属于管理活动，不是狭义构建 |

题目说“NOT part of construction”时，先找需求定义、项目整体规划。实际工程中阶段会交叠，考试按课程分类判断，不能因为编码前也需要思考就把所有规划都算 construction。

### 1.2 相邻扩展与变式预测

| 概念 | 正确理解 | 常见错误说法 |
|---|---|---|
| Construction with reuse | 使用现成组件实现当前功能 | “用了库就不用测试” |
| Construction for reuse | 把当前组件设计成未来可复用 | “只要复制代码就是良好复用” |
| Defensive programming | 对不合法输入、异常状态作有意义的处理 | “捕获所有异常并忽略最安全” |
| Profiling | 测量时间、调用次数、分配等，找实际瓶颈 | “凭代码行数能判断性能” |
| Verification | 检查实现是否符合规定 | 与 validation 完全等同 |
| Validation | 检查做出的东西是否满足用户实际需要 | 只要代码无异常就完成 |

**预测问法：**把“coding”换成“code review、unit testing、resource planning”，让你判断活动类别；或者问测试与调试的区别。

## 2. 软件工程伦理

**已考定位：**往年 2024 S1 MCQ8。

伦理题通常不是判断“能不能写出这段代码”，而是判断是否尊重隐私、公共安全、诚实与职业责任。

| 关键原则 | 看到什么场景要联想到它 | 更合适的行为 |
|---|---|---|
| Public interest 公共利益 | 产品可能伤害用户、泄露隐私或造成安全风险 | 识别和处理风险；公共利益不能简单让位于交付期限 |
| Client and employer 客户与雇主 | 雇主要求秘密收集用户信息 | 对雇主负责须与公共利益一致，不是无条件服从 |
| Product 产品 | 明知质量或安全缺陷仍隐瞒发布 | 如实报告，推动合理测试与修复 |
| Judgment 判断 | 为利益关系歪曲技术评估 | 保持独立、客观并披露利益冲突 |
| Management 管理 | 管理者要求伪造进度或压制风险报告 | 建立诚实、可追责的开发过程 |
| Profession 职业 | 虚假宣传能力、隐瞒重大错误 | 维护职业诚信 |
| Colleagues 同事 | 抢功、歧视、恶意阻碍他人 | 公平合作、合理评审 |
| Self 自身 | 不懂安全却声称已经验证可靠 | 持续学习并诚实说明能力边界 |

这八项是 IEEE-CS/ACM 软件工程伦理准则的组织方式。[准则原文](https://www.computer.org/education/code-of-ethics)

**排除规则：**“老板要求所以一定正确”“为了方便可以秘密收集”“只要没被发现就没问题”“用户点一次同意即可不受限制地使用数据”都不是可靠伦理理由。另一方面，“发现问题就立即向所有公众公开所有敏感资料”也不自动正确，应考虑证据、合适报告渠道和对他人的伤害。

**变式预测：**数据只为登录而收集，却用于广告画像；赶工跳过安全测试；隐瞒系统限制；发现同事漏洞后如何负责任地报告。

## 3. 知识产权与许可证

**已考定位：**往年 2025 S1 MCQ10、2024 S1 MCQ4；Quiz 01。

### 3.1 先分清保护对象

| 概念 | 主要保护什么 | 软件场景中的判断 |
|---|---|---|
| Copyright 版权 | 原创表达，而不是抽象思想本身 | 源代码、原创图像、文档等可能受保护 |
| Patent 专利 | 符合适用法律条件的发明 | 不能因为有“创新商业想法”就认定能获专利 |
| Trademark 商标 | 区分商品或服务来源的标识 | 应用名称、品牌标识更常在此讨论 |
| Trade secret 商业秘密 | 有商业价值且采取保密措施的信息 | 未公开算法实现、内部资料可能涉及 |
| Economic rights 经济权利 | 复制、传播、许可等经济利用相关权利 | 公开源码不等于放弃这些权利 |
| Moral rights 精神权利 | 作者署名、作品完整性等人格利益 | 具体范围依适用法域，不能简单等同于收费权 |

**应用题：**某 app 的原创图标和具体代码可以涉及版权；“做一个聊天 app”的功能想法、一般算法思想和名称本身，不因出现在 app 中就自动作为代码版权对象受到同样保护。图标也可能同时涉及商标。计算机相关发明的专利资格要另行判断。[IP Australia：计算机相关发明](https://www.ipaustralia.gov.au/patents/what-are-patents/what-computer-related-inventions-can-be-patented)

### 3.2 许可证判断表

| 情形 | 可以据此推出什么 | 不能据此推出什么 |
|---|---|---|
| Public GitHub repo，无 LICENSE | 代码可被公开查看；GitHub 平台规则允许相应查看与 fork 行为 | 任意复制、修改、分发、商用都获许可 |
| MIT | 宽松许可，允许广泛使用、修改、分发和商业利用，须遵守保留声明等条件 | 修改后必须全部按 GPL 开源 |
| GPL / copyleft | 分发受覆盖软件或衍生作品时会触发相应许可证义务 | 软件不能收费；所有私人修改必须立即公开 |
| Open source | 按开放源码许可证授予相应使用权 | 无版权、无条件、无成本、无责任边界 |
| Free software | 强调使用、研究、修改、分享的自由 | 必然价格为零 |
| Public domain | 不受版权专有权限制的状态，具体认定有法域差异 | 与“网页上能搜到”同义 |

无许可证时默认权利保留，不能把公开访问当作全面复用授权。[GitHub 许可证说明](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/licensing-a-repository)

MIT 要读清许可条件；GPL 允许销售，核心问题是分发时履行相应义务，而不是售价是否为零。[MIT 原文](https://opensource.org/license/mit)；[GNU 关于销售自由软件](https://www.gnu.org/philosophy/selling.en.html)

**变式预测：**把“下载”换成“重新发布修改版”；把 MIT 换成 GPL；把“算法具体实现代码”换成“算法思想”。每次都先问：保护的对象是什么？许可证授予什么权利？行为是私人使用还是对外分发？

## 4. 契约式设计、JML 与 Javadoc

**已考定位：**往年 2025 S2 MCQ4、2025 S1 MCQ9；Quiz 02。

### 4.1 谁负责哪一个条件

| 概念 | 通俗解释 | 例子 | 责任 |
|---|---|---|---|
| Precondition 前置条件 | 调用前必须满足什么 | 除数不能为 0 | 调用者应满足 |
| Postcondition 后置条件 | 正常返回后保证什么 | 返回值是两个数之和 | 被调用方法保证，前提是满足前置条件 |
| Invariant 不变式 | 对象在规定的可观察状态必须保持的性质 | 合法账户余额非负 | 对象方法共同维护 |
| Exceptional specification | 什么情况下抛出什么异常 | 参数非法时抛异常 | 按异常契约判断，不等同正常后置条件 |

不变式不是“执行每一条内部语句时都绝不可能暂时破坏”。它在什么边界需要成立取决于规范模型。

### 4.2 JML 关键字

JML（Java Modeling Language）用于描述 Java 程序行为规范，可用于静态验证或运行时断言检查。它不是 XML 文件读写工具。

| 写法 | 含义 |
|---|---|
| `requires P;` | 前置条件 P |
| `ensures Q;` | 正常返回的后置条件 Q |
| `invariant R;` | 类或对象不变式 R |
| `\result` | 当前方法的返回值 |
| `\old(e)` | 方法执行前表达式 e 的值 |
| `assignable ...;` | 允许修改哪些状态（扩展） |
| `signals (...) ...;` | 异常行为条件（扩展） |

例子是规范示意；这里限定输入避免 Java 整数溢出：

```java
//@ requires x >= 0 && x < Integer.MAX_VALUE;
//@ ensures \result == x + 1;
public int increment(int x) {
    return x + 1;
}
```

代入 `x = 3`：前置条件成立，正常返回必须是 `4`。代入 `x = -1`：调用者违反契约，不能仅凭这条正常契约要求方法产生某个指定结果。

账户扣款的后置条件可以写成 `balance == \old(balance) - amount`；`\old(balance)` 是扣款前余额。[OpenJML 前置条件](https://www.openjml.org/tutorial/Preconditions)；[后置条件](https://www.openjml.org/tutorial/Postconditions)；[不变式](https://www.openjml.org/tutorial/Invariants)

### 4.3 Javadoc 不等于 JML

```java
/**
 * Exchanges two elements.
 * @param <T> the element type
 * @param a the array
 * @param i the first index
 * @param j the second index
 */
public static <T> void swap(T[] a, int i, int j) {
    T temp = a[i];
    a[i] = a[j];
    a[j] = temp;
}
```

| 题目问什么 | 正确写法 |
|---|---|
| 参数 i 的说明 | `@param i the first index` |
| 类型参数 T 的说明 | `@param <T> the element type` |
| 返回值说明 | `@return ...`，通常用于非 void 方法 |
| 异常说明 | `@throws ExceptionType ...` |
| Java 泛型方法声明 | `<T>` 放在返回类型 `void` 之前 |

**原题纠错：**原题把 `@param` 放在 JML 语境中，但这是 Javadoc 标签；`public static void <T>` 也不是正确泛型方法声明。考试如果问注释选项，判断注释，不要把旁边错误代码记成模板。

**变式预测：**区分调用者与实现者责任；识别 `requires` 和 `ensures` 被写反；用 `\old` 描述余额变化；辨别注释只是说明，还是可被规范工具检查的约束。

## 5. 设计模式

**已考定位：**往年两道 Singleton；Quiz 03—11。模式题先看“什么在变化、什么想隐藏、谁依赖谁”，再选名字。

### 5.1 场景到模式总表

| 模式 | 中文 | 核心目的 | 题目中的典型信号 | 类别或备注 |
|---|---|---|---|---|
| Singleton | 单例 | 控制实例创建并提供统一访问 | Universe、唯一共享对象、私有构造器 | 创建型 |
| Factory Method / Factory | 工厂 | 把具体对象的创建从使用代码中分离 | 按操作系统创建不同对话框 | 工厂方法属于创建型；泛称 factory 不必严格等同某一 GoF 模式 |
| Template Method | 模板方法 | 固定算法骨架，某些步骤交给子类 | 流程不变、步骤实现不同 | 行为型 |
| Observer | 观察者 | 一个对象变化，通知多个订阅者 | 输入改变，多个 UI 组件同步 | 行为型 |
| Iterator | 迭代器 | 不暴露内部表示地依次访问元素 | CrazyList 支持 for-each | 行为型 |
| Facade | 外观 | 给复杂子系统提供简单统一入口 | 只公开 SpamFilter，隐藏内部处理类 | 结构型 |
| State | 状态 | 由当前状态对象决定行为与状态转移 | 众多布尔标记、状态相关分支 | 行为型 |
| DAO | 数据访问对象 | 隔离业务与存储访问细节 | 更换文件/数据库，业务少改 | 课程题归为 Structural；不是 GoF 23 模式之一 |

### 5.2 Singleton：构造器、静态引用、线程安全

```java
final class Universe {
    private static Universe instance;
    private Universe() {}
    public static Universe getInstance() {
        if (instance == null) {
            instance = new Universe();
        }
        return instance;
    }
}
```

| 代码位置 | 为什么需要 | 易错说法 |
|---|---|---|
| `private Universe()` | 普通外部代码不能直接 new | 只要 private 就必定实现了单例 |
| `static instance` | 类层面保存共享实例 | 每个调用者都有一个独立 instance |
| `static getInstance()` | 不必先创建对象就可取实例 | 返回 static 就等于返回新实例 |
| `if (instance == null)` | 延迟创建 | 每次调用都创建一个 |

普通单线程调用 `a = getInstance(); b = getInstance();` 后，`a == b` 为真，JUnit `assertSame(a,b)` 通过；通常 `assertEquals(a,b)` 也通过。它们通过的理由不同：前者直接检查同一对象，后者检查相等语义。

**线程变式：**上面的延迟初始化没有同步，两个线程可能都看到 null 并各自创建对象。不要把“单例意图”当成“实现自动线程安全”。简单的 eager initialization（饿汉式）可以写 `private static final Universe INSTANCE = new Universe();`，由类初始化机制创建；这是扩展写法，不是原题代码。

**判断：**私有构造器是常见手段；公共构造器通常允许外部 new，破坏常规单例控制。反射、序列化、多个类加载器等额外边界若题目没有给出，不要擅自引入改变基础题答案。

### 5.3 Factory：关注创建什么

```java
interface Dialog { void show(); }
// 具体类 WindowsDialog 和 MacDialog 均实现 Dialog。
// 工厂根据平台返回 Dialog，使用者只调用 dialog.show()。
```

原题跨操作系统对话框：客户端需要统一接口，创建过程决定具体平台类。若题目强调“一组相互兼容的按钮、菜单、窗口一起创建”，相邻扩展是 **Abstract Factory（抽象工厂）**；若由子类覆盖创建方法决定产品，则是 Factory Method。

### 5.4 Template 与 Strategy：最易混淆的一组

| 判断点 | Template Method 模板方法 | Strategy 策略（扩展） |
|---|---|---|
| 核心 | 固定步骤顺序，部分步骤可变 | 将一个算法封装成可替换对象 |
| 常见机制 | 继承并覆盖步骤 | 组合，持有策略接口 |
| 算法框架 | 基类通常规定骨架 | 客户端把任务委托给策略 |
| 典型场景 | `load → calculate → display` 流程固定 | 运行时换最短路线/最快路线算法 |

```java
abstract class RouteReport {
    public final void run() {
        load();
        calculate();
        display();
    }
    protected void load() { /* shared loading */ }
    protected abstract void calculate();
    protected abstract void display();
}
```

Quiz 物流题的预期选项是 Template，需结合给出的骨架和选项。现实描述仅说“算法与展示都可能变化”并不足以唯一锁定 Template；独立变化、组合替换时也可能讨论 Strategy 或 Bridge。**不要背成“只要算法变化就选模板”。**

### 5.5 Observer：通知，不是轮询所有组件

Subject（被观察对象）保存订阅关系；Observer（观察者）提供更新接口。输入框变化时通知已订阅组件。

| 常考判断 | 结论 |
|---|---|
| 可以有多个观察者 | 是，典型一对多 |
| 必须在 Subject 中写死所有具体 UI 类 | 否，可依赖观察者接口 |
| 新增观察者通常必须修改每一段 Subject 业务逻辑 | 否，注册机制用于减少这类修改 |
| 更新必然异步或多线程 | 否，普通同步回调也可实现 |
| 不再使用的观察者无需取消订阅 | 不一定，可能产生无效更新或对象保留问题 |

### 5.6 Iterator、Iterable 与 for-each

| 名词 | 作用 |
|---|---|
| `Iterable<T>` | 能提供迭代器，核心方法 `iterator()` |
| `Iterator<T>` | 保存某次遍历进度，核心方法 `hasNext()`、`next()` |
| `hasNext()` | 判断还有没有下一个元素 |
| `next()` | 返回下一个元素并推进；没有元素时通常抛 `NoSuchElementException` |
| `remove()` | 可选操作；并非所有迭代器支持 |

Java 增强 for 可以遍历数组，也可以遍历实现 Iterable 的对象。让 CrazyList 实现 Iterable 并提供 Iterator 是原题考点；只实现 Iterator 并不自动让容器支持增强 for。

| 相比先 `toArray()` | 可以成立的优势 | 不能过度推断 |
|---|---|---|
| 隐藏结构 | 调用者不必知道数组、链表或树的实现 | 完全没有任何实现成本 |
| 提前停止 | 找到目标后可停止后续访问 | `toArray` 必定深拷贝所有元素对象 |
| 额外存储 | 可避免先建立完整中间数组 | 所有迭代器都恒定空间，例如树迭代器可能维护栈 |
| 遍历中修改 | 某些迭代器提供受控删除等操作 | 任意修改集合都安全 |

Java 常见 fail-fast 迭代器可能在不合规结构修改时抛 `ConcurrentModificationException`，它不是并发安全保证。`toArray()` 通常复制元素引用，不会自动深拷贝每个对象。[ArrayList 文档](https://docs.oracle.com/en/java/javase/24/docs/api/java.base/java/util/ArrayList.html)

### 5.7 Facade 与可见性

`public SpamFilter` 提供统一调用入口；同包辅助顶层类省略访问修饰符，即 package-private，可以隐藏包外实现细节。Java 普通顶层类不能声明为 `private` 或 `protected`；嵌套类规则不同。

Facade 主要简化使用；Adapter 主要转换接口；Decorator 主要给对象叠加职责。三者都可能“包住另一个对象”，但目的不同。

### 5.8 State：状态对象决定行为

多个布尔值如 `isOpen`、`isClosed`、`isLocked` 可能出现互相冲突的组合。State 把状态行为与转移放进对应对象，Context（上下文）持有当前状态。

```java
interface DoorState {
    DoorState close();
}
// Context 中：state = state.close();
```

另一种设计是把 Context 传入状态方法，由状态调用 `context.setState(...)`。两种都可实现 State；Quiz 偏好“返回新状态”，理由是减少状态对象对 Context 的直接依赖。

| 命题 | 判断 |
|---|---|
| State 可减少到处出现的状态条件分支 | 通常正确 |
| 所有状态行为都应该完全相同 | 错，状态相关行为正是重点 |
| State 一定让总行数更少 | 错，往往增加类与接口 |
| 布尔变量在任何情况下都不能表示状态 | 错，简单二态问题可能足够 |
| 在接口新增无默认实现的方法，具体实现类须满足它 | 是，未实现的具体类无法正常编译 |
| 返回新状态可减少 Context 耦合 | 是，但不是唯一合法 State 实现 |

### 5.9 相邻模式扩展速查

| 模式 | 信号词 | 与已考模式的区别 |
|---|---|---|
| Adapter 适配器 | 旧接口与新接口不兼容 | 转换接口，不只是简化入口 |
| Decorator 装饰器 | 包装对象，逐层增加功能 | 侧重增加职责，不是转换接口 |
| Strategy 策略 | 可交换算法对象 | 选择算法；State 侧重对象状态及转移 |
| Command 命令 | 把请求变对象，排队、记录、撤销 | 请求本身被封装 |
| Composite 组合 | 叶子与容器统一处理成树 | 与 UML composition 不是同一个术语层次 |
| Builder 建造者 | 分步骤构建复杂对象 | 关注复杂构建步骤，而非仅选产品类型 |
| MVC | Model 数据、View 展示、Controller 输入协调 | 架构分工，不等于某一个 GoF 模式 |

**变式预测：**模式名称换成代码让你识别；问 State 与 Strategy、Facade 与 Adapter 的区别；问 singleton 的 `static` 被删后会怎样；问 Iterable 与 Iterator 哪个属于容器、哪个保存遍历进度。

## 6. Android

**已考定位：**往年 2025 S2 MCQ2、2025 S1 MCQ5、2024 S1 MCQ12；Quiz 12—13。

### 6.1 Activity 生命周期

Activity 可理解为应用中的一个交互界面组件。Callback（回调）是系统在状态变化时调用的方法，不是开发者按名字随便发明的状态通知。

```text
首次启动：onCreate → onStart → onResume
失去前台交互焦点：onPause
完全不可见：通常继续 onStop
从停止状态返回：onRestart → onStart → onResume
仅暂停后恢复：onResume
正常销毁路径：onDestroy（但进程被杀时不保证调用）
```

| 方法 | 主要含义 | 常见误区 |
|---|---|---|
| `onCreate()` | 创建实例、初始化 | 每次恢复前台都重新执行 |
| `onStart()` | 进入可见状态 | 所有应用都必须自己 override，否则编译失败 |
| `onResume()` | 进入前台可交互状态 | 与“首次创建”相同 |
| `onPause()` | 离开 resumed 状态 | 必然意味着已不可见或已销毁 |
| `onStop()` | 不再可见 | 必然马上执行 onDestroy |
| `onRestart()` | stopped 后重新启动 | 首次创建也必定经过 |
| `onDestroy()` | 实例被销毁时的回调 | 系统任何终止方式都保证执行 |
| `onClose()` | 不是标准 Activity 生命周期回调 | 名称听起来合理就选择 |

**打开新 Activity：**旧 Activity 通常先暂停；被完全遮住时通常停止。它可以留在返回栈，按返回键后恢复，并非打开新界面就立刻销毁旧实例。透明界面、多窗口、启动标志和任务设置可能改变具体情况，题目无特别条件时按普通流程判断。[Android 生命周期](https://developer.android.com/guide/components/activities/activity-lifecycle)

### 6.2 资源、Intent 与权限

| 考点 | 判断规则 |
|---|---|
| 默认字符串 | `res/values/strings.xml` |
| 西班牙语字符串 | `res/values-es/strings.xml`，同名资源提供不同语言值 |
| 资源引用 | 布局中常用 `@string/name`；Java 中使用资源 ID 如 `R.string.name` |
| Explicit Intent 显式意图 | 指定目标组件，如从当前 Activity 启动已知 Activity |
| Implicit Intent 隐式意图 | 描述动作和数据，由系统匹配能够处理的组件 |
| Manifest | 声明应用组件、权限等信息 |
| INTERNET 权限缺失 | 不能概括为 Java 编译错误；问题通常在联网能力或运行时出现 |
| Listener 监听器 | 不只按钮能使用，文本输入、列表等也可有监听机制 |
| Toast | 简短提示；不是完整 Activity，也不是长期交互窗口 |
| Layout 布局 | 决定组件的位置和尺寸，不等于业务数据模型 |

**扩展辨析：**Manifest 权限声明与运行时权限申请是不同问题；不是所有权限都弹窗申请。UI 状态恢复也不能只靠某个 Activity 对象永远留在内存中。

### 6.3 ConstraintLayout：先找被约束的两条边

Constraint（约束）描述“这个控件的哪条边，连到另一个控件的哪条边”。Start/End 是逻辑起点/终点，受从左到右或从右到左布局方向影响；默认英语布局中通常对应左/右。

Quiz 条件：

```text
element2 的 Start → element1 的 End
它的 End → element1 的 End
它的 Bottom → element1 的 Top，margin = 24dp
```

若 element2 固定宽度、默认水平 bias = 0.5，则其水平中心落在 element1 的 End 线上；并非整个 element2 都在右边。

具体代入：element1 右边 `x = 200`，element2 宽 `40`，则 element2 左边 `180`、右边 `220`。element1 顶边 `y = 100`，element2 高 `20`，底部向上隔 `24`，则底边 `76`、顶边 `56`。这里坐标只用于解释几何关系，实际尺寸单位需按 Android 布局换算。

**陷阱：**把 Start→End 误读为 Start→Start；只看一条水平约束；忽略固定宽度与 `0dp` match-constraints 的差别；忽略 bias 或 RTL。[ConstraintLayout 文档](https://developer.android.com/develop/ui/views/layout/constraint-layout)

**变式预测：**换资源语言代码；把界面从“完全遮挡”改成“半透明”；修改 bias、宽度、margin，让你判断相对位置。

## 7. 数据持久化与文件格式

**已考定位：**往年 2025 S1 MCQ7；Quiz 14—20。

Persistence（持久化）是把内存中的数据保存到文件、数据库等，让程序退出后仍能保留。Serialization（序列化）是把数据编码成可保存或传输的表示；deserialization（反序列化）是读回对象或数据。

### 7.1 格式选择总表

| 格式 | 擅长表达 | 优点 | 限制与陷阱 |
|---|---|---|---|
| CSV | 同结构的记录与列 | 简洁、表格工具友好、常适合按记录拆分 | 嵌套结构不自然；分隔符和换行需要正确解析 |
| JSON | 对象、数组、数字、字符串等 | 适合嵌套数据、跨语言常见 | 不会自动保留全部 Java 运行时类型信息 |
| XML | 树形元素、属性、文本 | 结构明确、工具生态成熟 | 标签可能增加体积；不能据此断言总是最慢最大 |
| Java 原生序列化 | 可序列化 Java 对象图 | 可保存对象关系 | 类兼容性、开销、安全边界需考虑；并非任意对象都能写 |
| 独立二进制文件 | 图片、音频等 | 不必转成冗长文本 | 元数据与文件路径需要共同管理 |

### 7.2 转义：字符能出现，不等于能原样出现

| 格式 | 要保存的内容 | 正确示意 |
|---|---|---|
| CSV | 一个字段中有逗号 | `"hello,world"` |
| CSV | 字段中有双引号 | `"He said ""Hi"""` |
| JSON | 字符串含双引号 | `"He said \"Hi\""` |
| JSON | 字符串含换行字符 | 使用转义 `\n`，不是把裸换行直接塞进 JSON 字符串 |
| XML | 文本中的 `<` 和 `&` | `&lt;` 与 `&amp;` |
| XML | 属性中与外层定界符相同的引号 | 例如双引号属性内用 `&quot;` |

CSV、JSON、XML 都能通过正确表示保存通常的可打印 ASCII 文本。不要扩展成“所有任意控制字符都可在 XML 中合法出现”。也不要把 CSV 引号规则误套成 JSON 的反斜杠规则。

**CSV 换行陷阱：**带引号字段可以含换行，所以“按每个物理换行直接切记录”不总是正确。

### 7.3 图片怎样保存

| 方案 | 是否合理 | 要记住什么 |
|---|---|---|
| 图片另存文件，JSON/CSV 保存路径或 ID | 合理，常见 | 路径有效性、移动与删除需要管理 |
| 将图片字节 Base64 编码后放进 JSON/XML | 合理 | 增加体积，不是压缩或加密 |
| 将 Image 对象直接 `toString()` 后当作图片保存 | 不合理 | 对象描述字符串通常不能还原图片 |
| 假定 `java.awt.Image` 自动可原生序列化 | 不成立 | Image 本身不实现 Serializable |

**扩展：**Base64 对 n 字节的主体编码长度通常是 `4 × ceil(n / 3)` 个字符，不含格式额外开销。3 字节常变 4 字符，体积约增加三分之一。

### 7.4 Gson 必背写法

```java
import com.google.gson.Gson;
import com.google.gson.reflect.TypeToken;
import java.lang.reflect.Type;
import java.util.Collection;

// 假设 Account 类存在，accounts 是 Collection<Account>。
Gson gson = new Gson();
String data = gson.toJson(accounts);
Type accountListType = new TypeToken<Collection<Account>>() {}.getType();
Collection<Account> restored = gson.fromJson(data, accountListType);
```

| 判断点 | 正确理解 |
|---|---|
| `toJson` | 对象 → JSON 文本 |
| `fromJson` | JSON 文本 → 指定目标类型 |
| `Account.class` | 可描述普通 Account 类型 |
| `Collection.class` | 只有原始集合类型信息，不能充分表达元素类型 Account |
| `TypeToken<Collection<Account>>` | 保留需要的泛型类型描述 |
| `new TypeToken<...>() {}` | 匿名子类形式中的 `{}` 有作用，别随意删掉 |
| `TokenType` | 原题写法有误，应是 Gson 的 `TypeToken` |

Java 的泛型类型擦除是这个题的关键。集合外壳对了不代表里面每个元素自动成为 Account。[Gson 用户指南](https://google.github.io/gson/UserGuide.html)

### 7.5 OpenCSV 字段绑定

假设无表头记录为 `id,brand,model,year,price`：

```java
@CsvBindByPosition(position = 3)
private int yearMade;
```

位置从 **0** 开始，所以第四列是 3。若使用带表头映射，可按实际表头写：

```java
@CsvBindByName(column = "year")
private int yearMade;
```

字段叫 `yearMade` 而表头叫 `year` 时，不应假定默认名称匹配会成功。分隔符是可配置的，不能把 CSV 限定为永远只能逗号；换成 `-` 后，同样需要考虑字段内容中的 `-` 与引号。[OpenCSV 文档](https://opencsv.sourceforge.net/)；[位置注解说明](https://opencsv.sourceforge.net/xref/com/opencsv/bean/CsvBindByPosition.html)

### 7.6 SAX 与 DOM

| 维度 | SAX | DOM |
|---|---|---|
| 模式 | 流式、事件驱动 | 构建文档树 |
| 处理方式 | 读取到标签、文本时触发处理 | 加载后沿节点访问、修改 |
| 主要内存特点 | 不必保留完整文档树，常适合大文件 | 通常需要存完整文档表示 |
| 随机回访某个节点 | 不如 DOM 直接，可能需自行保存信息 | 较方便 |
| 是否必然更快 | 不能一概而论 | 也不能一概而论 |

原题问 SAX 的主要优势，优先考虑 **降低完整文档常驻内存的需求**。如果应用把所有 SAX 事件结果又存成整棵树，仍可能用很多内存。

### 7.7 文件大小与分片

Quiz 对特定“数值占比较高、约 10KB 对象”的预期顺序是：`Serialized < CSV < JSON < XML`。这是题目情境下的估计，**不是任何数据都成立的定理**。字段名长度、标签、数字表示、对象描述开销、重复引用、压缩与数据量都可能改变顺序。

Sharding（分片）是把数据按某种规则分到多个部分。CSV 的记录结构常便于拆分；但要按逻辑记录解析，不能破坏带引号的多行字段。XML 属性并不会自动使文件可分片；JSON 使用 Gson 也不会自动实现数据库式分片。不存在“Java 对象只能序列化到 128 字节”的通用限制。

### 7.8 相邻扩展

| 考点 | 快速判断 |
|---|---|
| `Serializable` | 标记接口；可达对象图中涉及的对象也需符合序列化要求或被排除 |
| `transient` | 默认原生序列化时跳过该实例字段；不是自动加密 |
| `static` 字段 | 属于类，不作为对象的普通实例状态保存 |
| `serialVersionUID` | 与序列化类版本兼容性识别有关，不是对象 ID |
| JSON 的 null 与缺少字段 | 不总是同一业务含义，取决于映射与处理 |
| 压缩、编码、加密 | 分别解决体积、表示、保密问题，不能混为一谈 |

**变式预测：**交换 `toJson`/`fromJson`；把列号 3 改为 4；把元素类型 Account 换成嵌套泛型；比较大 XML 文件用 SAX 还是 DOM；问 Base64 是否压缩。

## 8. UML 类图

**已考定位：**往年 2024 S1 MCQ9；Quiz 21—23。

### 8.1 六种关系：看线型、箭头、端点

| 关系 | 英文 | 图形特征 | 指向/所在端 | 意义与代码线索 |
|---|---|---|---|---|
| 关联 | Association | 实线，可有可导航箭头 | 箭头指可导航目标 | 持有或认识另一个对象 |
| 依赖 | Dependency | 虚线普通箭头 | 使用者 → 被使用者 | 方法参数、返回类型或临时使用等 |
| 泛化/继承 | Generalization | 实线空心三角 | 子类 → 父类 | Java 类 `extends` |
| 实现 | Realization | 虚线空心三角 | 实现类 → 接口 | Java 类 `implements` |
| 聚合 | Aggregation | 实线空心菱形 | 菱形在整体端 | 较弱的整体—部分关系 |
| 组合 | Composition | 实线实心菱形 | 菱形在整体端 | 较强的整体—部分、所有权与生命周期约束 |

记忆：**三角指父类型，菱形放整体。** 普通实线箭头与空心三角不是一回事。源码有一个字段只能证明存在某种持有关系，不能仅凭字段就确定组合。

### 8.2 多重性与可见性

| 符号 | 含义 |
|---|---|
| `1` | 恰好一个 |
| `0..1` | 零个或一个 |
| `*` / `0..*` | 任意多个，包括零 |
| `1..*` | 至少一个 |
| `+` | public |
| `-` | private |
| `#` | protected |
| `~` | package visibility |
| 成员下划线 | 通常表示 static |
| 类/操作斜体 | 常用于 abstract |

如果 `A — B`，B 端标 `0..*`，意思是 **一个 A 可以关联零到多个 B**。别反读为一个 B 有多少 A。

### 8.3 原题实例与陷阱

| 原题关系 | 应用规则 |
|---|---|
| Car / Motorcycle 与 Vehicle | 若表示 is-a，子类向 Vehicle 画空心三角 |
| Floor 与 Spot | 若题设定义强整体—部分，组合菱形在 Floor；仍须依据题图 |
| UserDAO extends DAO | 泛化；箭头指 DAO |
| StateManager 持有 UserState | 关联，按题图读取多重性 |
| ConcreteState 与 State | State 是类则继承；State 是接口则实现，不能只看名字 |
| 方法返回 Iterator | 可形成对 Iterator 的依赖 |
| 某类 implements Iterator | 虚线空心三角指 Iterator |
| Notification Factory | 工厂依赖/创建具体产品；产品实现公共接口，别把工厂画成产品子类 |
| MyDAO 与 X | Quiz 指定图预期为实心菱形在 DAO 一侧，但“叫 DAO”本身不能证明组合 |

**变式预测：**把接口改成抽象类，箭头从虚线变实线；把 `1` 改成 `0..1`；把整体端菱形画到部分端；问局部参数和长期成员关联的区别。

## 9. 代码坏味道与重构

**已考定位：**往年 2024 S1 MCQ11、MCQ14。

Code smell 是提示可能有设计问题的迹象，不等于已证明有运行错误。Refactoring 是在保持外部可观察行为的前提下改善内部结构。

| 坏味道 | 看到什么代码 | 合适的改进 | 选择题陷阱 |
|---|---|---|---|
| Duplicated code | 两处重复累计热量 | 提取共享函数 | DRY 是原则，“违反 DRY”才是问题 |
| Poor naming | `displaySomething()` 看不出用途 | 改成表达意图的名称 | 变量越短越好 |
| Magic numbers / hardcoding | 状态、单位、规则散落为字面量 | 命名常量、配置或合适的类型 | 所有字面量都必须抽常量 |
| Long parameter list | 一个方法传很多松散参数 | 引入参数对象、按职责拆分 | 参数越少一定越正确 |
| Data clumps | 经度纬度、地点信息总一起出现 | 引入 Location 等值对象 | 任意几个参数都应合成一类 |
| Primitive obsession | 位置、类别全靠任意字符串 | enum 或专门类型 | 用字符串就绝对是错误 |
| Dead / unused code | DEFAULT_UNIT 定义后从未使用 | 核实用途后删除 | 有常量定义就是良好设计 |
| Long method / large class | 一类包办过多流程 | 提取方法、分离职责 | 类拆得越多越好 |
| Exposed state | 字段 public，任意外部修改 | 封装并提供有约束操作 | 自动加全部 getter/setter 就已实现良好封装 |
| Feature envy（扩展） | 方法主要操作别人的数据 | 考虑移动方法/重新分配职责 | 所有跨对象调用都是坏味道 |

### 9.1 Player、Team、Match 类的判断方法

- 先看有没有真正的 **is-a**：Player 是 Person 才可能适合继承；Player 有 Team 通常是 has-a 关联，不能为复用代码强行继承。
- Position 若是有限枚举集合，可用 enum 防止任意拼写值。
- 多处重复传地点信息时可引入 Location，避免参数散乱。
- Java 类继承类用 `extends`，实现接口用 `implements`；接口继承接口也用 `extends`。
- 将字段变 private 后，仍需考虑哪些修改是合法的；封装关注控制状态，不只是语法。

**变式预测：**给两个方案，问哪个在不改变行为下减少重复；让你区别“修复参数数量错误”与“重构设计”；把 enum、组合、继承混进同一组选项。

## 10. SOLID 设计原则

**已考定位：**往年 2025 S1 MCQ8、2024 S1 MCQ10；Quiz 24。

| 字母 | 名称 | 通俗判断 | 典型反例 |
|---|---|---|---|
| S | Single Responsibility 单一职责 | 一个模块围绕清晰职责组织，有相对一致的变化原因 | 同一个类管税费、界面、数据库、邮件 |
| O | Open/Closed 开闭原则 | 增加一种行为时优先扩展稳定抽象，而非不断改核心分支 | 每加一种食谱都改一大段类型判断 |
| L | Liskov Substitution 里氏替换 | 子类型能在需要父类型的地方使用且守住父类型契约 | 父类允许的输入，子类突然拒绝 |
| I | Interface Segregation 接口隔离 | 客户端不应依赖自己不需要的大接口 | 只读客户被迫实现删除与写入 |
| D | Dependency Inversion 依赖倒置 | 高层与低层通过抽象协作 | 业务流程写死某数据库具体类 |

### 10.1 OCP：扩展菜谱类型

已有 `Recipe.display()` 抽象接口，增加新 Recipe 实现，调用端仍 `recipe.display()`，通常更符合 OCP。若不断扩展 `if type == A / B / C` 并改动多处已有方法，扩展成本更高。

OCP 不是“已发布代码永远不能修改”。修 bug、调整不适合的抽象都可能需要改代码。题目比较的是新增变化是否被稳定接口隔离。

### 10.2 LSP：必须看契约，不只看继承语法

| 子类变化 | 通常是否符合替换要求 | 为什么 |
|---|---|---|
| 接受父类允许的全部输入，甚至更多 | 可以 | 不加强前置条件 |
| 原来接受 Vector2，现在只接受 Vector3 | 不符合原调用契约 | 缩小合法输入范围 |
| 原来承诺返回非负，现在可能负数 | 不符合 | 削弱后置保证 |
| 覆盖 getLength，返回正确三维长度 | 不因“覆盖”本身就违规 | 要看父类语义契约是否被破坏 |
| 字段 private | 不能由此断言违反 LSP | 访问控制与可替换性是不同问题 |
| 改为不可变对象 | 可能有益，但不自动修复接口契约冲突 | 仍须满足输入输出行为要求 |

Vector2 / Vector3 原题关注维度与参数契约。共同抽象 Vector 可以是改善方向，但必须设计一致的操作语义。

**Java 语法陷阱：**父类 `dilate(Vector2 v)`，子类写 `dilate(Vector3 v)`，通常是 **重载 overload**，不是对原方法的 **覆盖 override**。若子类保留 Vector2 参数却在内部强制转成 Vector3，则传入合法 Vector2 可能失败。两者都不能仅凭名字相同就认为实现了合法替换。

`(Vector2) vector3` 向上转型不把对象的 z 字段物理删除；引用的静态类型与对象的运行时类型不同。

### 10.3 相邻扩展：依赖注入不等于依赖倒置

Dependency injection（依赖注入）是通过构造器、参数等提供依赖对象的手段；DIP 是高低层依赖抽象的设计原则。注入一个被写死的具体类，不一定已经满足良好的抽象边界。

**变式预测：**辨认加强前置条件、削弱后置条件；区分“重写方法”与“违反 LSP”；问加入新功能时改分支还是加实现类；比较 extends 与组合。

## 11. Git 提交历史

**已考定位：**往年 2025 S1 MCQ1；Quiz 25—29。

### 11.1 三个区域、三个指针概念

| 名词 | 含义 |
|---|---|
| Working tree 工作区 | 当前编辑的文件 |
| Index / staging area 暂存区 | 准备进入下一次提交的内容 |
| Commit 提交 | 保存的版本快照及父提交等元数据 |
| Branch 分支 | 指向某个提交的可移动引用，不是把所有历史复制一份 |
| HEAD | 通常指向当前分支；detached HEAD 时可直接指提交 |
| `origin/main` | 本地保存的远程跟踪引用，反映最近获知的远程 main 状态 |

### 11.2 命令会移动什么

| 命令 | 主要效果 | 常见误判 |
|---|---|---|
| `git add file` | 更新暂存区 | 已生成提交 |
| `git commit` | 创建提交并推进当前分支 | 推进所有本地分支 |
| `git branch other` | 在当前位置创建 other 引用 | 自动切到 other |
| `git switch other` | 切换当前分支，HEAD 通常指向 other | 创建一个合并提交 |
| `git switch -c other` | 创建并切换分支 | 只创建不切换 |
| `git fetch` | 获取远程对象并更新相应远程跟踪引用 | 自动把远程内容合入当前分支 |
| `git merge feature` | 将 feature 合入当前分支 | 将当前分支合入 feature，无论当前在哪 |
| `git push` | 请求更新远程引用并传输需要的对象 | 一定成功，无论远程是否变化 |
| `git pull` | fetch 后按配置整合，可能 merge 或 rebase | 永远只下载，不整合 |

### 11.3 创建分支后的指针追踪

```text
初始：HEAD → main → H
执行 git branch other：HEAD → main → H；other → H
在 main 提交 J：HEAD → main → J；other → H
```

新提交推进当前分支 main，不会把 other 一起推进。HEAD 常仍然指向 main，跟随 main 间接到 J。[Git 分支原理](https://git-scm.com/book/en/v2/Git-Branching-Branches-in-a-Nutshell)

### 11.4 合并图的阅读方法

```text
* A (HEAD -> my_branch)
|\
| * B (origin/my_branch)
* | C
|/
* D
```

- A 有两个父提交 B、C，是合并提交；D 是两条线可见的共同祖先。
- 本地 my_branch 指 A；本地记录的 origin/my_branch 指 B。
- 不能仅凭线条判断谁是作者、有没有冲突、是否曾手工编辑。
- 不能仅凭本地图认定远程服务器此刻完全没变化；远程跟踪引用可能尚未刷新。
- 若远程仍在 B，A 已包含 B 的历史，推送到相应远程分支可能是快进更新；能否成功还受权限、保护规则与远程新变化影响。

### 11.5 Merge、fast-forward 与冲突

| 情况 | 判断 |
|---|---|
| 当前分支是目标分支祖先 | 常可 fast-forward，只移动指针，无须新合并提交 |
| 两条分支各有新提交 | 常需创建两个父节点的合并提交 |
| 两分支都修改文件 | 不代表必定冲突，修改内容可能可自动合并 |
| 有合并提交 | 不代表曾发生冲突 |
| 想把 feature 合入 main | 先确保当前是 main，再 merge feature |
| 想判断被删除文件 | 检查历史差异；不能只看当前目录 |

只读查询示例：`git log --oneline --graph --all --decorate` 看图；`git show <hash>` 看提交；`git log --diff-filter=D --summary` 查删除记录。Quiz 的短 hash 和“没有文件删除”仅适用于题设仓库，不能背成通用答案。

**扩展预测：**detached HEAD；revert 通过新提交撤销效果，reset 移动引用且模式影响暂存/工作区，二者不同；rebase 会重建提交导致提交 ID 改变。这些属于相邻概念，不表示本题集已经考过。

## 12. Tokeniser、Parser 与文法

**已考定位：**往年 2025 S2 MCQ3、2025 S1 MCQ6、2024 S1 MCQ7/13；Quiz 30。

### 12.1 三个阶段别混淆

| 阶段 | 中文 | 输入 → 输出 | 不应混同的工作 |
|---|---|---|---|
| Tokenisation / lexical analysis | 词法分析 | 字符 → token 序列 | 不负责完整句子结构是否正确 |
| Parsing / syntax analysis | 语法分析 | token → 语法结构/树 | 语法正确不必然意味着业务含义正确 |
| Semantic analysis / evaluation | 语义分析/求值 | 解释结构含义或算结果 | 不应当成所有 Tokeniser 自动完成的事 |

输入 `12 + 3`：可以形成 `INT(12), PLUS, INT(3)`；Parser 把它组织成加法结构；求值才得到 15。

| 概念 | 含义 |
|---|---|
| Token type | 类别，如 INT、IDENTIFIER、PLUS |
| Token value / lexeme | 具体内容，如 `12`、变量名 `a` |
| Buffer | 尚未处理的输入或缓存内容，具体含义看实现 |
| Peek / current | 通常查看当前 token 而不消费，但以代码为准 |
| Consume / takeNext | 通常消费并推进，但以题目提供的实现为准 |

**原题陷阱：**Tokeniser 不天然“区分大小写”或“不区分大小写”；这是词法规则决定的。`takeNext()`、`next()` 的准确行为不能只靠方法名猜，须看是否修改 buffer。

### 12.2 文法术语

| 名词 | 含义 | 示例 |
|---|---|---|
| Terminal 终结符 | 最终出现在输入中的符号 | `fetch`、`=`、`;` |
| Non-terminal 非终结符 | 需要继续展开的语法类别 | Sentence、Type、Identifier |
| Production 产生式 | 某类别允许怎样展开 | `Type → int | boolean` |
| Start symbol 开始符号 | 整句推导的起点 | S 或 Sentence |
| Derivation 推导 | 逐步替换非终结符 | S → Type Identifier ; → int c ; |
| Parse tree 语法树 | 展示产生式展开结构 | 根通常是开始符号 |
| Ambiguity 歧义（扩展） | 同一字符串有多个不同语法树 | 不等于“看起来句子长” |

### 12.3 判断合法字符串：逐项消费，不能漏终结符

原题文法的核心：

```text
S → Modifier Type Identifier ; | Type Identifier ;
Modifier → public | private | protected
Type → PrimitiveType | Identifier
PrimitiveType → int | double | boolean | void
Identifier → a | b | c | d | e | f
```

| 输入 | 按这份文法判断 | 理由 |
|---|---|---|
| `int c;` | 合法 | Type=int，Identifier=c |
| `private void a;` | 合法 | 文法明确允许 void，不可擅自换成 Java 编译规则 |
| `final int c;` | 不合法 | Modifier 中没有 final |
| `int blah;` | 不合法 | Identifier 不是任意 Java 名称，只允许 a—f |
| `int c` | 不合法 | 缺少分号 |
| `int c();` | 不合法 | 文法没有括号和方法声明形式 |
| `a b;` | 合法 | 第一个 Identifier 可作为 Type，第二个作为名称 |

**核心套路：**用给定规则，而不是用现实 Java 的习惯。文法接受不代表 Java 编译器一定接受；反过来也一样。

另一道 fetch 文法题：若产生式明确包含 `having id = int`，漏掉 `=` 就不合法；负整数能否出现看 int 的词法定义，不看自己对数据库的想象。

### 12.4 Sentence 根节点与主句动词

原题句子：`Dogs chase gray rabbits that talk to white rabbits`。

根语法类别是 Sentence。顶层拆成主语 noun phrase、主句 verb、宾语 noun phrase；主句动词是 **chase**。后面的 `that ...` 是宾语名词短语内部的关系从句，不把最后一个动词变成主句根。

注意题目问的是 **parse tree 的根语法符号** 还是简化后的 **AST 根运算/动词**：本题选项同时给出节点类型和字段，因此准确答案是 **a Sentence with verb="chase"**，不是一个单独的 Verb 节点。若其他题另行规定 AST 的简化表示，再按该表示判断。

### 12.5 相邻扩展：递归下降、优先级与剩余输入

```text
Expr → Term ( + Term )*
Term → Factor ( * Factor )*
Factor → INT | ( Expr )
```

这个写法让乘法比加法结合得更紧：`2 + 3 * 4` 的加法右侧先形成乘法子树，结果为 14。括号可改变结构，`(2 + 3) * 4` 为 20。

| 陷阱 | 正确判断 |
|---|---|
| 解析出一个合法前缀就算整句合法 | 若要求解析完整输入，还必须检查没有多余 token |
| 递归能处理任何写法而无需考虑 | 普通递归下降直接处理左递归可能无限递归 |
| 一条产生式只能递归一次 | 取决于规则，递归可以形成任意长度结构 |
| Tokeniser 报错与 Parser 报错相同 | 非法字符偏词法；合法 token 排列错误偏语法 |
| AST 与 parse tree 总是一模一样 | AST 常省略部分标点和中间语法类别 |

**变式预测：**漏分号/等号；增加规则中没有的修饰符；用多余尾部 token 测试是否消费完整输入；把主句与从句动词混淆；跟踪 buffer 每次消费后剩下什么。

## 13. 软件测试与覆盖

**已考定位：**往年 2025 S1 MCQ3、2024 S1 MCQ2/3；Quiz 31—36。

### 13.1 四种覆盖：分母不同，不能直接比较百分比

| 覆盖类型 | 100% 的基本意思 | 要计数的东西 |
|---|---|---|
| Statement coverage 语句覆盖 | 所有可执行语句至少执行一次 | 语句 |
| Branch / decision coverage 分支覆盖 | 每个判定的各个结果都走过 | 控制流分支/判定结果，按题设口径 |
| Condition coverage 条件覆盖 | 每个基本布尔条件取过真与假 | 复合表达式里的原子条件 |
| Path coverage 路径覆盖 | 所有要求覆盖的完整执行路径都走过 | 从入口到出口的路径 |

在通常的可达控制流模型、同一统计范围内：**100% 路径覆盖 ⇒ 100% 分支覆盖 ⇒ 100% 语句覆盖**。反方向一般不成立。若程序有不可达代码、不可行路径或循环，必须先看题目怎样定义覆盖集合；全路径覆盖可能不可实现。

#### 语句覆盖不等于分支覆盖

```java
if (x > 0) {
    y = 1;
}
return y;
```

只用 `x = 1` 可以执行所有这些语句，但没有走 `x > 0` 为假的出口。增加 `x = 0` 才覆盖该判定的另一个结果。

#### 分支覆盖不等于条件覆盖

考虑 `if (a || b)`，按短路求值，测试 `(true, false)` 和 `(false, false)` 能让整个判定一真一假；b 实际被求值时只有 false，没有覆盖 b 为真。

#### 条件覆盖不等于分支覆盖

考虑 `if (a ^ b)`，这里 `^` 是布尔异或。用 `(true,false)` 与 `(false,true)`：a、b 都取过真和假，但整个表达式两次都为 true，没走 false 分支。

### 13.2 70% 路径覆盖不能推出至少 70% 分支覆盖

100% 的包含关系不能机械套在任意百分比上。路径数和分支数的分母不同，而且许多路径可能共享大部分分支。

一个具体反例：入口分成 A/B 两条路线。A 内有四个独立二选一判定，共 16 条路径；B 内有一串互斥判定，共 4 个出口、4 条路径。总计 20 条路径。

- 只覆盖 A 中的 14 条不同路径：路径覆盖 `14/20 = 70%`。
- 整图二元判定结果数：入口 2，A 中 `4×2=8`，B 中 `3×2=6`，总计 16。
- 完全没进入 B，所以最多覆盖入口去 A 的 1 个分支和 A 的 8 个分支，即 `9/16 = 56.25%`。

所以原题不能从 70% path 推出 branch 至少也是 70%。

### 13.3 分支数、路径数、最少用例数是三个问题

以原题控制流为例：先判断 x 的 1/2/3/其他四类，再独立判断 y 的 1/2/3/4/其他五类。

```java
if (x == 1) { /* X1 */ }
else if (x == 2) { /* X2 */ }
else if (x == 3) { /* X3 */ }
// 否则为 Xother

if (y == 1) { /* Y1 */ }
else if (y == 2) { /* Y2 */ }
else if (y == 3) { /* Y3 */ }
else if (y == 4) { /* Y4 */ }
// 否则为 Yother
```

| 问题 | 结果 | 推导 |
|---|---:|---|
| 按每个二元判定两个结果计分支 | 14 | 共 3+4=7 个判定，每个 true/false |
| 可行完整路径组合 | 20 | 第一段 4 种 × 第二段 5 种 |
| 最少分支覆盖用例 | 5 | 每次可覆盖两段各一个类别，五类 y 至少需要 5 次 |
| 完整路径覆盖用例 | 20 | 独立且可行时，每次只走一个完整组合 |

实现 5 个分支覆盖测试的具体输入：

| 测试 | x | y | 覆盖类别 |
|---|---:|---:|---|
| 1 | 1 | 1 | X1、Y1 |
| 2 | 2 | 2 | X2、Y2 |
| 3 | 3 | 3 | X3、Y3 |
| 4 | 0 | 4 | Xother、Y4 |
| 5 | 0 | 0 | Xother、Yother |

为什么不需要 4+5=9 次？因为同一次调用能同时经过 x 段和 y 段。为什么不是 20 次？因为覆盖各分支不要求枚举所有跨段组合。

**适用边界：**“取较大值”只适用于这种能够自由组合、顺序执行的结构。嵌套、早返回、输入相关性可能让它失效。

### 13.4 短路 `&&` / `||` 怎么算

| 表达式 | 第一项 | 第二项是否执行 | 整体结果 |
|---|---|---|---|
| `a && b` | false | 不执行 | false |
| `a && b` | true | 执行，若 false | false |
| `a && b` | true | 执行，若 true | true |
| `a || b` | true | 不执行 | true |
| `a || b` | false | 执行，若 false | false |
| `a || b` | false | 执行，若 true | true |

`a && b` 的三种求值轨迹不等于“这个 if 有三个最终真假结果”。判定整体只有 true/false；若覆盖工具把短路子条件也建成控制流节点，则会细分分支。

#### 2024 checkAnswer 原题如何避免数错

原函数有外层三个类型判定、TEXT 内判定、NUMERIC 内复合判定、ANAGRAM 内判定，以及最后的 `if (isCorrect)`。

| 统计模型 | 分支数 | 最少用例的思路 |
|---|---:|---|
| 把 NUMERIC 的整个 `a && b` 视为一个判定 | 7 个判定 × 2 = 14 | TEXT 成败 2；NUMERIC 成败 2；ANAGRAM 成败 2；外层全部不匹配 1，共 7 |
| 把 NUMERIC 两个短路条件各作判定 | 8 个判定 × 2 = 16 | 数字部分需“非数字、数字但不等、数字且相等”3 类，合计 8 |

这些计数假设题目允许外层全部不匹配的输入，并排除意外异常。若枚举恰好只有这三类且契约禁止 null，外层最后 false 可能不可行，必须按允许输入域重新判断。原选择题未提供统一覆盖工具口径，因此不能把 14/7 或 16/8 当作脱离条件的唯一通用结论。

一个可行输入设计，允许为不同测试设置对应谜底：

| 类别 | answer | input | 目的 |
|---|---|---|---|
| TEXT | `cat` | `CAT` | 忽略大小写后 true |
| TEXT | `cat` | `dog` | false |
| NUMERIC | `12` | `12` | 左条件 true，右条件 true |
| NUMERIC | `12` | `13` | 左 true，右 false |
| NUMERIC | `12` | `abc` | 左 false，右不执行 |
| ANAGRAM | `abc` | `bca` | 排序后相等 |
| ANAGRAM | `abc` | `abd` | 排序后不相等 |
| 无匹配类型，若允许 | 任意 | 任意 | 外层三个判断全 false |

最后 `if (isCorrect)` 的 true/false 已被前面成功/失败用例覆盖，不需要凭空再加两次。

**隐藏陷阱扩展：**`matches("\\d+")` 不保证数值在 int 范围内，极大数字仍可能使 `parseInt` 抛异常；负号也不匹配该正则。别把“只含数字字符”当成“任何整数都可安全解析”。

### 13.5 JUnit 断言速查

以下按题集使用的 JUnit 4 语境。

| 写法 | 检查什么 | 易错点 |
|---|---|---|
| `assertEquals(expected, actual)` | 值或 equals 语义相等 | 通常期望值在前，实际值在后 |
| `assertSame(expected, actual)` | 是否同一对象引用 | 不能一般性用于字符串内容检查 |
| `assertNotSame(a, b)` | 不是同一对象 | 不代表内容不相等 |
| `assertTrue(condition)` | 条件为真 | 不会自动检查所有其他结果 |
| `assertFalse(condition)` | 条件为假 | 与 assertNull 不等价 |
| `assertNull(x)` | 引用为空 | 空字符串 `""` 不等于 null |
| `assertNotNull(x)` | 引用非空 | 不保证对象内部有效 |
| `assertEquals(expectedDouble, actualDouble, delta)` | 浮点近似相等 | delta 是允许误差，不是字符串参数 |
| `fail()` | 无条件失败 | 可用于到达不应到达的位置 |

反转字符串：若 `r = reverse("hello")`，用 `assertEquals("olleh", r)`。即使字符串驻留偶尔让 assertSame 通过，也不表示它适合验证字符串内容。

### 13.6 异常、超时、阶乘测试

```java
@Test(expected = IllegalArgumentException.class)

    factorial(-2); // 若上一行已按预期抛异常，这一行不会执行
```

| 阶乘输入 | 正确结果 |
|---|---:|
| 0 | 1 |
| 1 | 1 |
| 5 | 120 |
| 6 | 720 |

Quiz 展示代码将 5 和 6 的期望值对调，不能照抄。没有 factorial 方法体，不能推断某组测试已达完整语句或分支覆盖。测试通过也只说明这些检查通过，不能证明所有输入都正确。

### 13.7 JUnit 4 参数化测试正确骨架

```java
import java.util.Arrays;
import java.util.Collection;
import org.junit.Test;
import org.junit.runner.RunWith;
import org.junit.runners.Parameterized;
import static org.junit.Assert.assertEquals;

@RunWith(Parameterized.class)
public class ReverseTest {
    @Parameterized.Parameters(name = "{index}: reverse({0}) = {1}")
    public static Collection<Object[]> data() {
        return Arrays.asList(new Object[][] {
            {"hello", "olleh"},
            {"", ""},
            {"a", "a"}
        });
    }

    @Parameterized.Parameter(0)
    public String input;

    @Parameterized.Parameter(1)
    public String expected;

    @Test
    public void reversesText() {
        String actual = new StringBuilder(input).reverse().toString();
        assertEquals(expected, actual);
    }
}
```

| 检查位置 | 正确要求 |
|---|---|
| Runner | `Parameterized.class`，不是把普通 runner 当参数化 runner |
| 数据方法 | 公共、静态，返回 runner 支持的参数集合/数组 |
| 每一行 | 对应一组参数；`Object[][]` 的每一行必须是数组 |
| 注入字段 | 此种字段注入写法用 public 实例字段 |
| 参数下标 | 从 0 开始，`@Parameter` 不写数值默认 0 |
| 测试方法 | JUnit 4 普通 `@Test` 是 public、void、无参数的实例方法，不是 static |
| 多个字段 | 避免所有字段都漏下标而重复使用 0 |

假设测试不同算法实现，可写 `new Object[][] { {new Imp1()}, {new Imp2()} }`，不能写成二维数组里直接放非数组的 `new Imp1()`。[JUnit Parameterized 文档](https://junit.org/junit4/javadoc/4.13/org/junit/runners/Parameterized.html)

### 13.8 相邻测试扩展

| 概念 | 做题规则 | 简单例子 |
|---|---|---|
| Equivalence partition 等价类 | 按预期相同行为分输入类别 | 年龄有效/太小/太大 |
| Boundary value 边界值 | 测边界及相邻点 | 合法 1—100，考虑 0、1、2、99、100、101 |

## 13A. 性能分析：Amdahl 定律

**已考定位：**Quiz 37。

Amdahl 定律说明：只加速一部分程序时，未加速部分会限制整体提升。

设原总时间为 T，可加速部分占比 p，该部分加速 s 倍：

```text
新时间 Tnew = T × [(1 − p) + p / s]
整体加速比 S = T / Tnew = 1 / [(1 − p) + p / s]
时间减少比例 = 1 − Tnew / T
当 s → ∞，整体最大加速比 = 1 / (1 − p)，前提 p < 1
```

### 原题代入：80% 的部分加速 5 倍

| 步骤 | 计算 |
|---|---|
| 假设原时间 100 秒 | 被优化 80 秒，未优化 20 秒 |
| 被优化部分新时间 | 80 / 5 = 16 秒 |
| 总新时间 | 20 + 16 = 36 秒 |
| 整体加速 | 100 / 36 ≈ 2.7778 倍 |
| 时间减少 | (100 − 36) / 100 = 64% |
| 无限加速的极限 | 100 / 20 = 5 倍 |

**错误选项：**整体加速 5 倍；直接算 `0.8×5`；把时间减少 64% 叫加速 64 倍；把 `36%` 当作节约时间比例。

**变式预测：**给目标加速比反求局部 s：`s = p / [1/S − (1−p)]`。分母为正才有有限正解；若目标超过极限，单靠优化这部分无法达到。

若多个不重叠部分分别被优化，可用 `Tnew/T = 剩余比例 + Σ(pi/si)`。若优化有额外通信或管理开销，需要把开销计入，不能直接假设理想模型仍完全准确。

## 14. 树与数据结构选择

**已考定位：**往年 2025 S2 MCQ1、2025 S1 MCQ4、2024 S1 MCQ5/6；Quiz 38—45。

### 14.1 基本名词与高度口径

| 名词 | 含义 | 陷阱 |
|---|---|---|
| Root 根 | 没有父节点的起点 | 根不一定是最小值 |
| Leaf 叶 | 没有真实子节点的节点 | 红黑树 NIL 叶与画出的键节点叶需区分 |
| Depth 深度 | 根到该节点的距离 | 常按边数，根深度为 0 |
| Height 高度 | 节点到最深叶的最长距离 | 有的题按边数，有的按层数 |
| Balanced 平衡 | 满足某种规定的高度约束 | 不等于完全对称 |
| Complete binary tree 完全二叉树 | 除末层外满，末层从左向右填 | 与 AVL、BST 不是同一定义 |
| Full binary tree（常用定义） | 每个节点有 0 或 2 个孩子 | 英文教材术语可能不同，依定义判断 |

按边数：单节点树高度 0，常令空树高度 −1。按节点/层数：单节点高度 1，空树常为 0。**先确定口径再选数值。**

### 14.2 四种遍历

```text
        4
      /   \
     2     6
    / \   / \
   1   3 5   7
```

| 名称 | 顺序口诀 | 上图结果 |
|---|---|---|
| Preorder 前序 | 根、左、右 | 4 2 1 3 6 5 7 |
| Inorder 中序 | 左、根、右 | 1 2 3 4 5 6 7 |
| Postorder 后序 | 左、右、根 | 1 3 2 5 7 6 4 |
| Level-order 层序 | 一层一层，从左到右 | 4 2 6 1 3 5 7 |

前序不是“先所有左节点”，后序不是“把前序反过来”。必须对每个子树递归使用同一规则。

Quiz 原图的字母标签不是普通字母大小顺序的 BST；遍历时按图连接关系，不可自己按字母重排。对应结果：

```text
前序：Q T N S P W X M R V Y O U
后序：N W P S T R Y O V M U X Q
```

因此前序中 M 前后是 X、R；后序中 Y 前后是 R、O。

**扩展预测：**中序有序是 BST 的性质，不是任意二叉树的性质；前序第一个是根，后序最后一个是根；层序通常用队列，DFS 遍历常用递归栈或显式栈。

### 14.3 BST：先比较，再往一侧走

Binary search tree（二叉搜索树）的基本性质：左子树键小于当前键，右子树键大于当前键；重复键如何处理由题设决定，不能随便安排。

```java
Node find(Node node, int key) {
    if (node == null) return null;
    if (key == node.key) return node;
    if (key < node.key) return find(node.left, key);
    return find(node.right, key);
}
```

搜索只进入可能的一侧。普通 BST 不保证平衡，最坏可以退化成链，查找/插入/删除达到 O(n)。

#### 原题插入与高度

按顺序插入 `80, 97, 49, 2, 20, 52, 25, 9, 27, 76`：

```text
          80
         /  \
       49    97
      /  \
     2    52
      \     \
      20    76
     /  \
    9   25
          \
          27
```

最长路径 `80 → 49 → 2 → 20 → 25 → 27`：5 条边、6 个节点。按边数高度为 5，按层数为 6。

### 14.4 BST 删除三种情况

| 被删节点 | 操作 | 易错项 |
|---|---|---|
| 0 个孩子 | 从父节点断开 | 不需要找后继 |
| 1 个孩子 | 让父节点接到其唯一孩子 | 不能丢掉整个子树 |
| 2 个孩子 | 用中序后继或前驱替换，再删除替代节点原位置 | 不能任意选一个叶子替换 |

- **Successor 后继：**有右子树时，右子树最左节点。
- **Predecessor 前驱：**有左子树时，左子树最右节点。
- 替代节点原位置最多一个孩子，所以之后可以化简为前两种情况。
- 复制键/值与移动节点引用是不同实现方式，但都要保持结构与键值对应关系。

Quiz 删除 M 采用后继，沿其右子树向左找到 **Y**；采用前驱的算法也可能选 R，但必须符合题目指定策略。不能仅看字母顺序猜。

### 14.5 AVL：四种旋转一次分清

AVL 是每个节点左右子树高度差至多 1 的 BST。取平衡因子 `BF = height(left) − height(right)`，合法值是 −1、0、1；若教材使用相反定义，符号相反但树的判断不变。

插入后从新节点往上检查，找到最低的失衡祖先 z，判断从 z 到插入点先走哪边、再走哪边。

| 类型 | 路径 | 操作 | 三键例子 |
|---|---|---|---|
| LL | 左、左 | 对 z 右旋 | 插入 30,20,10 → 根 20 |
| RR | 右、右 | 对 z 左旋 | 插入 10,20,30 → 根 20 |
| LR | 左、右 | 先左旋 z 的左孩子，再右旋 z | 插入 30,10,20 → 根 20 |
| RL | 右、左 | 先右旋 z 的右孩子，再左旋 z | 插入 10,30,20 → 根 20 |

**旋转必须保持中序顺序。** 旋转移动的不只是三个节点，还要正确接回中间子树；它不会改变键的大小关系。

#### 往年：根 7 的树插入 6

```text
插入后：             LR 修复后：
       7                    5
      / \                  / \
     3   9                3   7
    / \                  /   / \
   2   5                2   6   9
        \
         6
```

失衡点是 7；路径先左到 3，再右到 5，所以 LR。先对 3 左旋，再对 7 右旋，根变 5。

#### Quiz：根 5 的树插入 6

```text
插入后：             RL 修复后：
     5                      7
    / \                    / \
   2   8                  5   8
      / \                / \   \
     7   9              2   6   9
    /
   6
```

失衡点 5，先右到 8，再左到 7，所以 RL。先对 8 右旋，再对 5 左旋。

**扩展：**AVL 删除也可能引起失衡，且修复可能继续传播到祖先；不能把插入的局部恢复直觉机械用于全部删除情形。

### 14.6 红黑树：先检查性质，再做修复

普通红黑树的常用性质：

1. 每个节点为红或黑。
2. 根为黑。
3. 空孩子 NIL 视为黑色。
4. 红节点不能有红孩子，即不能红红相邻。
5. 从任一节点到其后代 NIL 的各路径，黑节点数相同。

“红节点只能是叶子”是错的；“每条路径红节点数相同”是错的；“左右子树高度差必须 ≤1”是 AVL 规则，不是红黑树规则。红黑树仍须满足 BST 的有序关系。

#### Black-height 黑高怎么数

先统一是否计起点、是否计 NIL。对同一起点比较不同路径时采用相同口径即可；相同路径约定下黑节点数必须一致。不要有的路径数 NIL、有的不数。

例如根 10B，左 5B，右 15B，没有其他真实孩子：从根到任一 NIL 都经过两个真实黑节点和一个 NIL，黑数一致。如果把 5 改红而其他不变，左右黑数不一致，即使没有红红相邻也不合法。

#### 插入修复表：普通父节点/叔叔版本

新键先按 BST 插入，通常涂红。Parent 是父，Grandparent 是祖父，Uncle 是祖父的另一个孩子；不存在的叔叔按黑 NIL。

| 情况 | 处理 |
|---|---|
| 新节点是根 | 涂黑 |
| 父为黑 | 不产生红红冲突，通常无需修复 |
| 父红、叔红 | 父与叔涂黑、祖父涂红，然后向祖父继续检查；最后根保持黑 |
| 父红、叔黑，内侧 LR/RL | 先旋转父节点，把它变成外侧形状 |
| 父红、叔黑，外侧 LL/RR | 对祖父旋转并适当交换/调整颜色，消除红红冲突 |

**算法口径：**左倾红黑树（LLRB）还有额外约束，其中间步骤与普通红黑树算法可能不同。精确画图题要沿用题设实现；不能只看“最后是合法红黑树”就认为符合指定过程。

#### 2025 S2：插入 25

```text
插入前：                 插入后：
       30B                     30B
      /   \                   /   \
    20B   34B               20R   34B
   /   \                   /   \
 10R   23R                10B   23B
                                  \
                                  25R
```

25 插在 23 右侧。父 23 红、叔 10 红，所以先变色；祖父 20 变红，其父 30 黑，到此结束，不需要旋转。

中序 `10,20,23,25,30,34`；前序 `30,20,10,23,25,34`；后序 `10,25,23,20,34,30`。最长路径 3 条边。选项若写中序 `20,10,...`，不用完整模拟颜色也能由 BST 中序有序性排除。

#### 2024 S1：依次插入 16、34、18、40、57、15

按上述普通插入修复规则，可得：

```text
       /   \
```

后序为 `15R,16B,34R,57R,40B,18B`。关键是插入 18 时先处理内侧折线；插入 40 时发生红叔变色；插入 57 时处理右侧外侧失衡。

### 14.7 复合键：区间不是随便比较

Quiz 的区间键按 `(start, end)` 字典序：先比 start，只有 start 相同才比 end。因此 `(2,8) < (2,11) < (5,10) < (5,15) < (8,14) < (9,16)`。

不是按区间长度排，也不是只看是否重叠。插入 `(9,16),(5,15),(5,10),(8,14),(2,11),(2,8)`，按题目普通红黑树规则，对应前序：

```text
(5,15)B, (2,11)B, (2,8)R, (5,10)R, (9,16)B, (8,14)R
```

**相邻扩展：**真正用于区间重叠查询的 interval tree 可能额外维护子树最大终点；题目仅使用区间作为有序键时，不应自行添加未给出的增广规则。

### 14.8 B 树：一个节点能放多个键

B-tree 是多路平衡搜索树。一个节点里有 k 个有序键，内部节点通常有 k+1 个孩子；所有叶子位于同一深度。

**“阶”的定义必须先看题设。** 若 order m 表示最多 m 个孩子，则最多 m−1 个键，非根内部节点至少 `ceil(m/2)` 个孩子。另一些教材用最小度数 t 定义，此时最多 2t 个孩子、2t−1 个键。不要混用公式。

Quiz 三阶 B 树按最多 3 个孩子、2 个键理解：

```text
删除前：            删除 14 并借位后：
      [5,12]                [5,10]
     /  |   \              /  |   \
   [3][8,10][14]          [3] [8] [12]
```

步骤：

1. 删除右叶的 14，该叶变空，低于非根最少键数。
2. 左兄弟 `[8,10]` 有多余键，可借。
3. **不是直接把 10 丢到右叶。** 先将父分隔键 12 下移到右叶。
4. 将兄弟最大键 10 上移替换父中的 12。
5. 得父 `[5,10]`，三个孩子 `[3]、[8]、[12]`，所有区间关系仍正确。

| 删除后情形 | 常用处理 |
|---|---|
| 节点键数仍足够 | 不必调整 |
| 兄弟有富余键 | 经父分隔键借位/重分配 |
| 相邻兄弟都无富余 | 与兄弟及父分隔键合并，父可能继续下溢 |
| 根变空且只剩一个孩子 | 该孩子成为新根，树高减一 |

**扩展预测：**B 树插入满节点时分裂并提升中间键；B+ 树通常将记录集中在叶子且叶子相连，适合范围扫描；具体阶数和记录存储约定仍看题设。

### 14.9 结构选择与复杂度

以下为典型实现与假设，不把接口名称当复杂度保证。

| 结构 | 按键查询 | 插入/删除 | 适合场景与限制 |
|---|---|---|---|
| 未排序数组/ArrayList | 一般 O(n) 搜索；按下标 O(1) | 尾部追加摊还 O(1)，中间移动 O(n) | 随机索引、紧凑存储 |
| 有序数组 | 二分查找 O(log n) | 维护顺序通常 O(n) | 查询多、修改少 |
| LinkedList | 一般 O(n) 定位 | 已有目标节点/位置时链接修改可 O(1) | 不要把定位成本漏掉 |
| 普通 BST | 平均取决于形状，最坏 O(n) | 最坏 O(n) | 无自动平衡保证 |
| AVL / 红黑树 | O(log n) | O(log n) | 按键有序、范围、最小最大 |
| HashMap | 良好散列等假设下平均 O(1) | 平均 O(1) | 高频精确键查询，不保证排序 |
| Map 接口 | 不指定统一实现复杂度 | 不指定 | HashMap 与 TreeMap 行为/代价不同 |
| 二叉堆（扩展） | 看堆顶 O(1)，任意键查找通常 O(n) | 插入/删堆顶 O(log n) | 优先队列，不是普通 BST |

按用户 ID 高频查询且频繁增删，题设无排序要求时通常选择 HashMap 类映射。若 ID 连续、范围小，数组也可直接按 ID 索引；如果 ID 很稀疏或动态范围很大，直接数组可能浪费空间。若要求按 ID 有序遍历或范围查询，平衡搜索树更有理由。

**额外速查：**HashMap 的键相等与哈希应一致，Java 中通常要求相等对象有相同 hashCode；哈希冲突不代表两个键相等。不能把平均 O(1) 当最坏永远 O(1)。

### 14.10 树题通用操作顺序

1. 先写比较规则：数字、字典序还是自定义 comparator。
2. 按规则完成普通 BST 插入/查找定位。
3. 按指定树种修复：AVL 看高度，红黑树看父叔颜色，B 树看键数。
4. 保留所有子树，检查中序/区间有序性。
5. 最后按题目要求算颜色、遍历、高度；别在插入未结束时就选答案。

## 考场最后检查

| 看到题干 | 先做这件事 |
|---|---|
| NOT、FALSE、incorrect | 圈出否定词，别选了正确陈述 |
| Select all | 每个选项单独判断，不默认只有一个答案 |
| Always、never、guarantee | 检查是否缺少必要条件，尤其复杂度、线程、大小、生命周期 |
| Minimum tests | 找必须分别执行的互斥类别，再看哪些可以一次组合覆盖 |
| Branch / path / condition | 先写清统计对象，不直接用同一个数 |
| Tree height | 先确定边数还是层数 |
| Tree insertion | 先定位，再修复，最后遍历 |
| UML | 先认线型和箭头形状，再看端点 |
| Git | 先找 HEAD 指哪个分支，再移动对应引用 |
| Grammar | 严格按给定规则，检查整段输入都被消费 |
| API code | 看导入、方法方向、泛型、static、参数下标与可见性 |
| Scenario design | 找变化点与依赖关系，避免只按关键词选模式 |
